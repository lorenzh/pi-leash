# Add the owned child-process stdio adapter

Status: draft
Approach: Add a Node infrastructure adapter that directly launches one validated local executable and returns an `OwnedStdioProcess` that itself implements `AcpTransport`, including its process-independent eventual `closed: Promise<void>`, as the single transferable owner of piped stdio and child shutdown.
Source work item: none (trackerless project; user request dated 2026-07-24)

## Problem

pi-leash defines `OwnedProcess`, `OwnedProcessSpawner`, and `AcpTransport` ports but has no production adapter connecting them to a Node child process, so later delegation work cannot safely launch a configured ACP agent, exchange bytes over local stdio, observe failures, transfer one coherent owner between lifecycle layers, or guarantee bounded cleanup without duplicating or abandoning responsibility for a live child.

## User stories

- As a delegation implementer, I want one named stdio/process object to be both the child owner and ACP byte transport so that ownership cannot split between a detached process handle and transport.
- As a maintainer, I want executable validation and direct argument passing without a shell so that untrusted launch data cannot become shell syntax.
- As an operator, I want launch failures, child exits, and bounded stderr observations to be diagnosable without leaking sensitive child output into logs or retaining unbounded data.
- As a lifecycle owner, I want bounded close attempts plus process-independent eventual closure observation so that incomplete cleanup retains ownership without abandoning a live child or falsely reporting success.

## Acceptance criteria

- AC-1: The production adapter resides outside the ACP and application core and defines an explicit exported composite type named `OwnedStdioProcess` that directly implements both `OwnedProcess` and `AcpTransport`, including `readable`, `writable`, `close()`, and `readonly closed: Promise<void>`. `AcpTransport.closed` is a process-independent completion signal: its public contract identifies only actual closure of all transport-owned backing resources and exposes no PID, exit status, process signal, or process-cleanup policy. There is no detached child transport with separate ownership. From the instant Node creates a child handle until successful launch returns, the adapter owns that same object; successful launch transfers it to the launch caller. When the caller invokes spec 003's selected `connect(ownedStdioProcess, attemptSignal)` API, neither this adapter nor `OwnedStdioProcess` interprets or retains the caller-owned `attemptSignal`. The caller remains the immediate owner of the exact object until spec 003 publishes successful connection resolution. If connect rejects or otherwise never publishes successful transfer, the caller closes that object; successful resolution transfers the exact object to the returned connection owner through its `AcpTransport` view. After transfer, higher layers close only the connection owner and never separately close descendant transport or process handles. Launch failure or launch abort before return remains the adapter's cleanup responsibility, leaving exactly one immediate owner at every observable acquisition stage.
- AC-2: Before starting a child, the launch boundary rejects an empty, relative, NUL-containing, missing, non-file, or non-executable command path and rejects an absent/non-directory working directory without creating a process; it accepts an absolute local executable such as `process.execPath`, preserves argument boundaries, and passes only the caller-supplied environment entries rather than implicitly merging the parent environment.
- AC-3: For accepted input, the adapter launches the executable directly with shell use disabled, supplies arguments as discrete values, and configures stdin, stdout, and stderr as pipes. A deterministic fixture proves that spaces, quotes, dollar signs, command separators, and redirection characters arrive as literal argument bytes and cannot create a marker file or execute a second command.
- AC-4: A successful launch returns the `OwnedStdioProcess` itself as the transferable `AcpTransport`: its `writable` sends bytes to child stdin, its `readable` receives bytes from child stdout, its bounded `close()` governs one complete stream-and-child cleanup attempt, and its process-independent `closed` promise remains available to any owner through only the `AcpTransport` view until all backing resources actually close. Byte order and content are preserved, stdout is never mixed with stderr, stream backpressure is honored, and child-side EOF or stream failure becomes observable to the corresponding Web Stream consumer without falsely settling `closed` while any backing resource remains open.
- AC-5: If Node cannot complete the spawn after validation, including an executable disappearing or becoming unlaunchable between validation and spawn, the launch operation rejects with an actionable typed error identifying the launch operation and executable without including arguments, environment values, or raw stderr; no `OwnedStdioProcess` is transferred, the adapter closes every stream/listener it created, and it retains ownership until it proves that no child remains running.
- AC-6: After a successful spawn, ordinary exit code `0`, non-zero exit, and signal termination each settle `OwnedProcess.exited` exactly once using the existing `number | null` contract, close or error the transport endpoints consistently, and remain observable even when exit occurs immediately. Child exit starts or completes final release of adapter-owned streams, listeners, timers, and handles; `closed` resolves exactly once only after that release is complete. An exit before or during a caller's `close()` does not hang or trigger an inapplicable termination operation, and an exit observed after a cleanup-incomplete attempt still drives final release without requiring another `close()` call.
- AC-7: Stderr is continuously drained so that a child cannot block on a full stderr pipe, is excluded from ACP stdout, and is never written automatically to project logs or copied into thrown errors. Under the contract selected in OQ-2, each `OwnedStdioProcess` has one declared positive-integer `stderrLimitBytes`; at most that many stderr bytes are retained or exposed for the process, all excess bytes are discarded without backpressuring the child, and observation reports deterministically whether truncation occurred. The OQ-2 resolution must place the exact retrieval/callback shape, retained-byte selection rule, decoding responsibility, default and maximum bound, and truncation representation into this AC before approval; tests cover the exact bound, one byte over it, sustained excess stderr, and sensitive sentinel text without incidental console/log output.
- AC-8: An already-aborted launch request starts no child and reports abort. If launch aborts after child creation but before successful launch return transfers ownership, the adapter invokes or joins the active `OwnedStdioProcess.close()` attempt under the same `ProcessCleanupPolicy` as explicit close. After successful launch return, the caller may pass the exact object and its caller-owned `attemptSignal` to spec 003 as `connect(ownedStdioProcess, attemptSignal)`; this adapter and `OwnedStdioProcess` neither interpret nor retain that connect-attempt signal. Until spec 003 publishes successful transfer, later caller cancellation and any resulting close remain the caller-owner's responsibility; after transfer, cleanup reaches `OwnedStdioProcess.close()` only through the returned highest owner's close path. This adapter neither defines nor schedules the higher-level whole-run `timeoutMs`; its cleanup bounds begin only when a close attempt starts and use the distinct names in AC-9. Repeated abort delivery and abort racing with exit or an active close join that active attempt and do not duplicate its stream-close or termination operations, alter a settled exit result, settle `closed` without actual resource closure, or release ownership while the child may remain live.
- AC-9: `OwnedStdioProcess.close()` is safe before or after natural exit and provides bounded, retryable cleanup with concurrent-attempt deduplication. `AcpTransport.closed` is a resolve-only process-independent `Promise<void>`: it resolves exactly once only after child exit is proven and every adapter-owned stream, listener, timer, and child-process handle is closed or released; it does not resolve or reject because a bounded close attempt fails and may remain pending indefinitely while actual closure is unproven. Each close attempt uses a `ProcessCleanupPolicy` containing three distinct positive finite bounds—`gracefulCloseMs`, `terminateWaitMs`, and `forcedExitWaitMs`, never the whole-run `timeoutMs`—and a documented monotonic clock. For a live child, an attempt ends stdin and waits at most `gracefulCloseMs`, invokes the OQ-1-selected supported-platform termination operation and waits at most `terminateWaitMs`, then invokes the selected forced-termination operation and waits at most `forcedExitWaitMs` for proven exit and final resource closure; natural exit skips inapplicable later operations. A close call resolves only after `closed` resolves. If an attempt's bounded stages finish while `closed` remains pending, that call rejects through the `AcpTransport` view with a typed `ProcessCleanupIncompleteError` carrying stable code `cleanup_incomplete`; the same `OwnedStdioProcess` remains observable and owned with all resources needed to detect later exit and finish closure, and no layer may abandon it or report successful ownership release. Calls overlapping one active attempt share that attempt's one promise and result without repeating side effects. An incomplete result is not permanently cached: a later nonconcurrent `close()` starts a new bounded attempt, first rechecks `closed` and observed exit, skips completed or inapplicable work, and applies OQ-1's approved per-retry signal rules; it again rejects `cleanup_incomplete` if its bounds expire before `closed` resolves. A later child exit drives final resource closure and resolves `closed` even without another close call, after which every later `close()` resolves successfully without side effects. Every downstream connection, run, retained session, scheduler slot, and shutdown operation that still owns this chain remains nonterminal and occupied while `closed` is pending and may become terminal or release capacity only after it observes `closed` resolve. OQ-1's supported platforms, exact operations/signals and per-retry rules, default and maximum values, and clock/deadline behavior must be copied into this AC before approval.
- AC-10: Focused Vitest unit and integration coverage records red-green-refactor evidence and uses only repository-controlled Node fixtures plus an injected child-process/clock seam where an operating-system failure cannot safely be induced. Coverage exercises validation, literal argv, byte transport, immediate and non-zero exits, asynchronous spawn failure, stderr pressure, pre/post-spawn abort, graceful exit, ignored graceful termination, forced termination, concurrent close-attempt deduplication, sequential close retry, exact ownership before and after spec 003 publishes transfer from `connect(ownedStdioProcess, attemptSignal)`, including proof that the adapter and object neither interpret nor retain `attemptSignal`, process-independent `AcpTransport.closed`, and cleanup-incomplete behavior. The tests require no network, credentials, timing-dependent vendor behavior, or installed vendor executable; every real fixture PID is proven exited, and adapter-created streams, listeners, timers, and child-process handles do not remain active after proven cleanup. Cleanup-incomplete cases prove that the bounded `close()` call rejects with the typed incomplete failure, overlapping calls observe one deduplicated attempt, the exact same `OwnedStdioProcess` remains observable and owned, `closed` remains pending, and downstream terminal/capacity release is prohibited. They then prove that a later simulated exit causes final resource closure and resolves `closed` without another close call, after which a later `close()` succeeds; the OQ-1-selected behavior for a sequential retry before exit is also covered. `npm run check`, `npm run typecheck`, `npm run test:unit`, `npm run test:integration`, `npm test`, and `npm run build` then exit `0`, and the same change updates the `AcpTransport` contract plus affected process-lifecycle, local-stdio, architecture, and security documentation.

## Non-goals

- Defining or loading the user-facing executable, argument, environment, whole-run `timeoutMs`, or harness configuration owned by spec 005.
- Implementing ACP framing, initialization, capability negotiation, sessions, prompts, attempt-signal interpretation, cancellation semantics, or connection policy owned by spec 003; this spec references only the selected `connect(ownedStdioProcess, attemptSignal)` API and the boundary at which spec 003 publishes successful ownership transfer.
- Registering Pi tools or commands, integrating with Pi lifecycle events, or changing the no-op extension factory.
- Supporting remote transports, shells, terminal/PTY transports, detached children, daemons, or vendor-specific process adapters.
- Persisting process state, stderr, diagnostics, or launch history.
- Supporting concurrent delegated runs, shared process pools, process reuse, or cross-run coordination.
- Defining how connection, run, retained-session, scheduler, or host-shutdown owners project the process-independent `closed` signal; this spec only requires those owners not to bypass or abandon the highest owner while `closed` is pending.
- Sandboxing the child or reducing operating-system permissions beyond direct, validated launch inputs and the explicitly supplied environment.

## Open questions

- OQ-1 — Process cleanup policy and supported-platform termination semantics: Which operating systems are supported; which exact Node operation or signal performs the terminate and forced stages on each one; after a cleanup-incomplete result, which completed stages remain suppressed and which terminate/forced operations may repeat on each later sequential attempt; what exact defaults and allowed maxima apply to `gracefulCloseMs`, `terminateWaitMs`, and `forcedExitWaitMs`; and which monotonic-clock, deadline-anchor, and boundary behavior governs every initial and retry attempt? The cleanup-incomplete lifecycle is not open: a bounded attempt whose deadline expires before actual closure rejects with `ProcessCleanupIncompleteError` code `cleanup_incomplete`, ownership remains observable and nonterminal, `closed` remains pending, concurrent calls deduplicate, later actual child/resource closure resolves `closed`, and every later close then succeeds; no option may cache incomplete failure permanently, report false success, or abandon a possibly live child. The recommended policy choice is to support only platforms covered by deterministic CI and use documented Node child-process operations per platform. This cleanup policy is distinct from the higher-level whole-run `timeoutMs`. **Owner:** project maintainer. **Approval blocker:** choose the supported-platform matrix, exact operations/signals and per-retry suppression/repetition rules, all three default and maximum bounds, and monotonic clock/deadline semantics; copy them into AC-9 and its deterministic tests before approval.
- OQ-2 — Stderr observation surface: Should callers receive a bounded retained tail, bounded structured chunks through a callback, or both; which bytes are preserved when `stderrLimitBytes` is exceeded; and who decodes bytes? The recommended choice is a byte-capped retained tail with explicit truncation metadata and no automatic logging, because it remains observable without creating an unbounded or backpressure-sensitive second consumer. **Owner:** project maintainer. **Resolution:** choose the public shape, retained-byte rule, decoding responsibility, exact default and maximum `stderrLimitBytes`, and truncation representation; copy them into AC-7 and its boundary tests before approval.

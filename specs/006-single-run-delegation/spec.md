# Single-run delegation lifecycle

Status: draft
Approach: Compose specs 003–005 behind one Pi-independent application run owner that serializes states and sanitized events, linearizes `connect(ownedStdioProcess, attemptSignal)` so cancellation before success keeps caller ownership while success transfers ownership to the connection, emits at most one terminal outcome only after proven cleanup, and retains only the highest owner in observable `cleanup_incomplete` until its eventual closure is proven.
Source work item: none (trackerless project; user request dated 2026-07-24)

## Problem

pi-leash has typed ACP, process, configuration, and delegation boundaries but no application service that owns a delegation run from bounded agent resolution through one ACP turn and non-abandoning hierarchical cleanup. Without one run owner, Pi integration or infrastructure adapters would have to coordinate untrusted working-directory input, deadlines, cancellation, event sanitization, terminal races, ownership transfer, and process disposal themselves, creating inconsistent outcomes, sensitive-data exposure, duplicate close attempts, or abandoned child processes.

## Approach

Use one application-layer **run owner** as the sole authority for a delegation run's state, exported events, terminal outcome, and cleanup coordination. It composes the single-agent resolver from spec 005, the `OwnedStdioProcess` adapter from spec 004, and the ACP connection/one-turn operation from spec 003 through typed ports. The spec-004 `OwnedStdioProcess` implements `AcpTransport`: the run owner holds that same object before ACP connection and calls exactly `connect(ownedStdioProcess, attemptSignal)`. If attempt cancellation linearizes before connect success, caller ownership remains and connect cannot later succeed; if success linearizes first, ownership transfers to the connection and a later abort cannot reclaim it. The connection owner then owns complete descendant cleanup through its retryable `close()` and eventual `closed` promise. If cleanup remains incomplete, the run owner stays observable and occupied, retains and observes only its highest owner, and emits no terminal outcome until that owner's eventual closure is proven.

## User stories

- As an application integrator, I want one Pi-independent operation for a single delegated turn so that every outer interface invokes identical core behavior.
- As a caller, I want ordered sanitized typed run events and one eventual terminal outcome so that I can report progress without interpreting ACP frames or exposing configured secrets.
- As a maintainer, I want one run owner and an explicit typed ownership chain so that cancellation, timeout, failure, and cleanup never close one resource through competing layers or abandon an unconfirmed child.
- As a contributor, I want deterministic lifecycle, sanitization, race, and cleanup tests so that behavior can change without credentials, vendor harnesses, or nondeterministic timing.

## Lifecycle contract

A run accepts one configured-agent selection understood by spec 005, one untrusted `requestedCwd` candidate, one turn request understood by spec 003, and cancellation through its typed application contract. It passes `requestedCwd` only to the spec-005 resolver; no raw candidate reaches process or ACP ports. Resolution returns the canonical configured-agent identifier, final validated `cwd`, launch/environment values, profile `runTimeoutMs`, and the normalized finite readonly `redactionValues` contract. Only the resolved `cwd` reaches specs 004 and 003; only `redactionValues` supplies configured-value patterns to the application sanitizer.

The run owner accepts no caller-provided final working directory, config-load bound, run timeout, or deadline override. Spec 005 supplies a separate finite config-load bound available before resolution starts. That bound and the resolver's `AbortSignal` constrain `created`/`resolving`. On successful resolution, the run owner anchors the profile's `runTimeoutMs` immediately after resolution; resolution time is not deducted from `runTimeoutMs`. Config-load-bound expiry is a typed configuration-resolution failure, while `runTimeoutMs` expiry is the run's `timed_out` terminal trigger. During connection acquisition, caller cancellation or `runTimeoutMs` expiry aborts the run-owned `attemptSignal` passed as the second argument to `connect`. After successful connect, cancellation acts only through the transferred connection owner and its active turn; it never authorizes direct closure of the former transport owner. Spec-004 cleanup-stage bounds remain separate and may continue after a terminal trigger is selected.

**Configured-agent identifier** means exactly the canonical validated profile identifier returned by spec 005. It is the only agent identity exported by this contract; executable paths, arguments, working directories, environment names or values, vendor metadata, and raw invalid selection input are not alternative identifiers and are not emitted as public diagnostic identity.

The lifecycle has these monotonic states:

1. `created` — the run has been accepted but resolution has not started and no external resource is acquired.
2. `resolving` — exactly one configured agent and untrusted `requestedCwd` are being resolved through spec 005 under its config-load bound.
3. `starting` — the resolved launch, including only its final `cwd`, is creating one `OwnedStdioProcess` through spec 004.
4. `running` — the same object has transferred through its `AcpTransport` interface to a spec-003 connection owner and one ACP initialize/session/prompt turn is in progress.
5. `cleaning_up` — no new work may start; the run owner is closing only its highest successfully acquired owner.
6. `cleanup_incomplete` — the highest owner's close could not yet prove complete descendant cleanup; this state is observable and nonterminal, that owner remains retained, the run observes and retries cleanup only through that owner, no capacity-release or terminal signal is emitted, and only its public eventual-closure contract may prove cleanup complete.
7. `terminal` — complete descendant cleanup is proven, the highest owner is released, and the single terminal outcome is immutable.

The normal path is `created → resolving → starting → running → cleaning_up → terminal`. Cancellation, config-load failure, `runTimeoutMs` expiry, or another failure may move any earlier nonterminal state to `cleaning_up`. An incomplete close moves `cleaning_up → cleanup_incomplete`; only successful eventual-closure proof from the retained highest owner permits `cleanup_incomplete → terminal`. No state moves backward or leaves `terminal`. If closure is never proven through that owner, the run remains `cleanup_incomplete`, observable, owned, occupied, and nonterminal indefinitely rather than falsely reporting completion.

### Acquisition and cleanup ownership

`OwnedStdioProcess` is the one transferable object: spec 004 returns it as the immediate child/stdio owner and it implements the exact `AcpTransport` interface accepted by spec 003. Ownership transfer is based on successful acquisition, not on a cast, attempted call, or partial initialization.

| Highest successful acquisition | Immediate ownership | Run-owner cleanup |
| --- | --- | --- |
| No `OwnedStdioProcess` returned | The called spec-004 operation retains any partial child allocation | Abort the call; close no lower resource directly |
| `OwnedStdioProcess` returned; `connect(ownedStdioProcess, attemptSignal)` has not successfully linearized, including rejection or attempt cancellation | The run owner holds that object, which owns its child and complete stdio transport | Close and, after an incomplete attempt, retry only that `OwnedStdioProcess` through its public owner contract |
| `connect(ownedStdioProcess, attemptSignal)` successfully linearizes | The connection owner holds the same object through `AcpTransport`; its close owns complete transport and child cleanup | Close and, after an incomplete attempt, retry only the connection owner through its public owner contract |

Attempt cancellation and successful connect resolution form one ownership linearization. If `attemptSignal` aborts first, connect rejects with typed cancellation, leaves the `OwnedStdioProcess` with the run owner, and cannot resolve successfully later; the run owner closes that object. If connect succeeds first, ownership transfers atomically to the returned connection owner; a simultaneous or later abort cannot return ownership to the caller, and all cancellation and cleanup proceeds only through the connection owner.

The run owner never retains a second transport owner after successful connect, never separately closes the transferred `OwnedStdioProcess` or child, and never bypasses a connection owner after its close reports incomplete cleanup. When the retained highest owner is the connection, an incomplete close leaves the run nonterminal and occupied while it observes only `connection.closed` and invokes any sequential cleanup retry only through the retryable `connection.close()` contract; concurrent calls join the current attempt. A failed or incomplete retry is not closure proof. Only successful resolution of `connection.closed` proves eventual descendant closure, permits release of that connection owner, and allows the pending sanitized terminal outcome. Before transfer, the equivalent rule applies only through the retained `OwnedStdioProcess` public close/exit contract. Descendant transport, process, and child handles are never observed or closed around either owner.

### Sanitized export boundary

The application contract exports only project-owned sanitized types, such as `SanitizedRunEvent`, `SanitizedRunOutcome`, and `SanitizedDelegationError`; raw ACP updates, raw dependency errors, and unsanitized result types remain internal. The run owner performs sanitization before every event, outcome, or error crosses this boundary. Pi integration in spec 007 receives only these sanitized values and is not responsible for discovering configuration or receiving secret values.

The run consumes exactly spec 005's normalized finite readonly `redactionValues` from the resolved profile as the configured-value matcher. It does not derive, append, canonicalize, case-fold, decode, or otherwise broaden patterns from environment entries, executable, arguments, cwd, authentication guesses, credential-shaped text, raw diagnostics, or any other source. Before export, every exact occurrence of a `redactionValues` member in a permitted string field is replaced with the stable marker `[REDACTED]`, including repeated and overlapping occurrences; longest members match first. For streamed fields, let `L` be the longest member length under spec 005's validated length unit. The sanitizer retains at most `L - 1` trailing units that could prefix a member before releasing a chunk, so a member split across any number of chunks is redacted exactly and the pending suffix is strictly bounded by spec 005's validated per-member maximum. An empty `redactionValues` vector retains no suffix.

Projection is structural before value matching. Prompts, raw `requestedCwd`, resolved `cwd`, executable, argument vector or values, raw stdio frames, raw dependency errors, and unknown thrown values are never copied from internal state or diagnostics into an exported shape. A version-pinned project classification table covers every field that spec 003 can normalize; fields classified as protocol-sensitive are removed rather than copied, including at minimum tool-call `rawInput`, `rawOutput`, raw metadata, and location paths. Neither structural executable/argument/cwd exclusion nor classified-field removal adds values to `redactionValues` or relies on matching their text.

Only permitted model-generated text and structured fields proceed to recursive exact matching against `redactionValues`. The configured-agent identifier is the sole allowlisted agent identity. A string absent from `redactionValues` and not removed by structural or protocol-field classification is not claimed to be detected as a secret, even if it resembles credentials or independently equals an internal configured value.

Exactly one terminal outcome may be selected from this tagged set, but it is emitted only after complete descendant cleanup is proven:

- `completed` — spec 003 returned a validated ACP stop response that the approved cancelled-stop mapping classifies as normal completion.
- `cancelled` — caller cancellation or an ACP `stopReason: cancelled` won and maps to cancellation under the approved cancelled-stop and terminal-trigger rules.
- `timed_out` — profile `runTimeoutMs` expired and won under the approved terminal-trigger rule; a later ACP cancellation acknowledgement cannot create a second outcome.
- `failed` — configuration resolution, startup, process, transport, protocol, turn, or completed-cleanup reporting failed and won under the approved error and terminal-trigger rules.

`cleanup_incomplete` is a state and sanitized nonterminal event, never a terminal outcome or synonym for `failed`. A provisional terminal trigger may be retained internally while cleanup is incomplete, but no terminal event/outcome promise settles until the retained highest owner's eventual-closure contract proves cleanup and permits `terminal`. The later event and outcome remain sanitized under the same export boundary. The exact event surface, cancelled-stop mapping, error precedence, and simultaneous terminal-trigger precedence remain approval-blocking decisions under Open questions.

## Acceptance criteria

- AC-1: The application layer exports a typed single-run contract, run-owner implementation, and sanitized event/outcome/error types whose production import graph contains no dependency on `src/pi/`, Pi APIs, UI code, vendor adapters, or vendor-specific identifiers; architecture tests enforce this boundary, documentation reserves `run owner` for this role, and spec-007-facing types expose no raw configuration secret, ACP update, process handle, or unsanitized error field.
- AC-2: The run input contains exactly one configured-agent selection, one untrusted `requestedCwd`, one turn request, and cancellation; starting a valid run invokes the spec-005 resolver once with the selection, candidate, and signal under spec 005's separate config-load bound, starts at most one spec-004 `OwnedStdioProcess`, calls exactly `connect(ownedStdioProcess, attemptSignal)`, and invokes at most one spec-003 ACP turn. The run owner obtains the configured-agent identifier, final `cwd`, environment, `runTimeoutMs`, and normalized finite readonly `redactionValues` only from the resolved profile; an already-aborted run invokes none of those operations and emits one sanitized terminal outcome. If cancellation or `runTimeoutMs` aborts `attemptSignal` before connect success linearizes, connect rejects without transfer or any possible late success and the run owner closes its `OwnedStdioProcess`; if connect success linearizes first, the connection owns that same object and a simultaneous or later abort can act only through the connection owner.
- AC-3: Unit tests observe only `created`, `resolving`, `starting`, `running`, `cleaning_up`, `cleanup_incomplete`, and `terminal` and prove every transition follows this spec. Tests prove `cleanup_incomplete` remains observable, nonterminal, and occupied with the highest owner retained and no capacity-release/terminal signal. When that owner is a connection, the run observes only its eventual `closed` promise, retries cleanup only by calling its retryable `close()`, and transitions to `terminal` only after `closed` resolves successfully; incomplete or failed retries, or descendant exit observed outside that owner, do not terminalize the run.
- AC-4: On the successful path, the run owner forwards untrusted `requestedCwd` only to spec 005, passes only the resolved final `cwd` and launch values to spec 004, supplies the same returned `OwnedStdioProcess` to spec 003 with exactly `connect(ownedStdioProcess, attemptSignal)`, preserves the sanitized validated turn result and `stopReason`, closes only the connection owner after transfer, and publishes one sanitized `completed` outcome under the approved cancelled-stop mapping and only after `connection.closed` proves closure.
- AC-5: The run exposes ordered sanitized lifecycle/turn events and at most one sanitized terminal outcome; all nonterminal events precede it, `cleanup_incomplete` emits no terminal signal, and late ACP messages, process exits, promises, cancellation requests, timers, or close settlements produce neither an out-of-order event nor a second outcome. An event consumer can distinguish `cleanup_incomplete` from all terminal tags without inspecting free text.
- AC-6: Cancellation is idempotent in every nonterminal state: it aborts resolution/startup work, aborts `attemptSignal` while connect is pending, requests ACP cancellation only when a turn is active after transfer, enters hierarchical cleanup through the highest owner, and eventually emits the single sanitized outcome selected by the approved mapping/precedence rules only if that owner's closure is proven. Repeated or post-terminal cancellation has no additional effect; cancellation that loses the connect-success race cannot reclaim `OwnedStdioProcess`, and cancellation in `cleanup_incomplete` does not bypass or discard the retained owner, release capacity, or fabricate a terminal outcome.
- AC-7: The run owner accepts no caller config-load bound, timeout, or deadline override. Tests prove spec 005's separate config-load bound is active before resolution and its expiry produces a sanitized typed configuration-load failure without starting a process; successful resolution anchors profile `runTimeoutMs` immediately afterward with no deduction for resolution elapsed time; `runTimeoutMs` expiry triggers cancellation/cleanup and the approved `timed_out` race semantics; and spec-004 `gracefulCloseMs`, `terminateWaitMs`, and `forcedExitWaitMs` remain distinct cleanup bounds.
- AC-8: Every thrown, rejected, malformed, unsupported, premature-exit, or cleanup condition is normalized into a sanitized exported delegation error that identifies only the exact configured-agent identifier when available, failed run operation, stable code, and actionable recovery guidance. Exported diagnostics are built from an allowlisted shape rather than copied from raw causes: raw unknown causes, executable/vendor/harness identifiers, argument vectors or values, requested/resolved cwd values, environment data, ACP payloads, classified protocol fields, and cleanup handles are structurally absent before `redactionValues` matching. Their exclusion neither depends on textual matching nor broadens that matcher; a cleanup-incomplete report is represented as a typed sanitized nonterminal event rather than a terminal error.
- AC-9: Before every event, outcome, or error export, the run owner first applies structural projection and classified-protocol-field removal, then exact configured-value replacement using only spec 005's normalized finite readonly `redactionValues`. Parameterized tests cover each normalized spec-003 event variant and field; every `redactionValues` member at string start/middle/end; repeated and overlapping members with longest-member-first behavior; a maximum-length member divided across two or more chunks; nested arrays/objects; successful output, cancellation, timeout, primary/cleanup failures, and serialization. Tests prove the streaming pending suffix is at most `L - 1` in spec 005's validated length unit and therefore bounded by its per-member maximum; executable, argument, and requested/resolved-cwd sentinels plus classified protocol fields are absent from exported diagnostics even when those sentinels are not matcher members; no `redactionValues` member appears on any public or captured diagnostic surface; and a distinct near-match absent from `redactionValues`, allowed non-sensitive content, and the configured-agent identifier remain intact. No test or implementation derives a broader matcher or claims arbitrary unknown-secret detection.
- AC-10: Ownership tests use object identity to prove spec 004's returned `OwnedStdioProcess` implements `AcpTransport`, remains held by the run owner until `connect(ownedStdioProcess, attemptSignal)` succeeds, and is the same object transferred to the connection owner. Before return the run owner closes nothing. A cancellation-before-success race proves connect rejects, caller ownership remains, the run closes only `OwnedStdioProcess`, and a delayed SDK callback cannot produce late success or transfer; a success-before-cancellation race proves ownership transfers and the run thereafter closes only the connection owner. If connection close yields `cleanup_incomplete`, the run retains that connection, emits only the sanitized nonterminal state, releases no capacity, observes only `connection.closed`, and directs every retry only to `connection.close()`; it never calls the transport or process descendant. An eventual-closure test proves `closed` resolves only after cleanup is proven and only then permits the pending sanitized terminal outcome, while a never-proven-closure test keeps the run observable, occupied, and nonterminal without an unhandled rejection or abandoned handle.
- AC-11: Deterministic unit race tests use controllable promises, barriers, and injectable monotonic schedulers to cover connect success versus `attemptSignal` cancellation in both orders, an attempted late connect success after abort, normal completion versus cancellation, completion versus `runTimeoutMs`, cancellation versus timeout, process exit versus ACP completion, primary failure versus completed-cleanup failure, connection close returning `cleanup_incomplete` versus eventual `closed` resolution and retryable close, unsolicited `stopReason: cancelled`, non-cancelled stop after cancellation, and cancellation during every nonterminal state. Every schedule yields the approved winner, one highest-owner cleanup path with no descendant bypass, sanitized exports only, no terminal/capacity release while cleanup is incomplete, and at most one eventual terminal outcome after closure proof.
- AC-12: `npm run test:integration` builds and spawns only the deterministic fake ACP agent over local stdio and selects finite scripted scenarios for: streamed output followed by `stopReason: end_turn`; a spec-005 `redactionValues` member in one chunk and split across chunks; classified tool-call fields; structural diagnostic sentinels for executable, arguments, and requested/resolved cwd that are not matcher members; local cancellation acknowledged by `stopReason: cancelled`; unsolicited `stopReason: cancelled`; cancellation racing a non-cancelled stop; JSON-RPC errors from each of `initialize`, `session/new`, and `session/prompt`; malformed or SDK-invalid protocol input; child exit before a prompt stop response; a prompt held past profile `runTimeoutMs`; clean exit; forced-termination exit; and delayed proven exit after the connection owner's close first reports `cleanup_incomplete`, with only its eventual `closed` promise permitting terminalization. Protocol barriers replace timing-dependent sleeps, tests require no network, real credentials, or vendor executable, every exported event and outcome is sanitized, and every real fixture PID is proven exited before its test ends.
- AC-13: The change updates architecture, ACP, configuration-handoff, and security documentation for the run owner, untrusted `requestedCwd`, config-load bound, post-resolution `runTimeoutMs` anchor, exact `connect(ownedStdioProcess, attemptSignal)` ownership linearization, exact consumption of spec 005's finite normalized `redactionValues`, the validated-maximum-bounded streaming suffix, structural diagnostic projection and classified-field removal, connection-level retryable close and eventual `closed` proof, `cleanup_incomplete`, capacity retention, cancelled-stop mapping, precedence rules, and eventual cleanup; fresh `npm run check`, `npm run typecheck`, `npm run test:unit`, `npm run test:integration`, `npm test`, and `npm run build` all exit 0.

## Non-goals

- Registering Pi tools or commands or depending on Pi APIs, modes, sessions, TUI, RPC, JSON, or print behavior.
- Persisting run history, events, outcomes, ACP sessions, or agent state.
- Running concurrent delegations, queues, batches, retries, scheduling, rate limiting, or backpressure across runs; schedulers must nevertheless treat `cleanup_incomplete` as active and retain capacity.
- Performing more than one ACP turn, sending follow-up prompts, or implementing mid-turn steering beyond cancellation supplied by spec 003.
- Accepting caller-provided final `cwd`, config-load bounds, `runTimeoutMs`, process-cleanup bounds, or deadlines, or defining the configuration and resolution policy owned by spec 005.
- Defining process spawning, `OwnedStdioProcess` internals, child supervision, cleanup bounds, termination mechanics, or descendant eventual-exit mechanics owned by spec 004; this run observes cleanup only through its retained highest owner's public closure contract.
- Defining ACP negotiation, ACP-session creation, protocol decoding, connection internals, cancelled-stop wire semantics, or turn mechanics owned by spec 003.
- Requiring spec 007 or another outer adapter to read configuration, receive spec 005's `redactionValues` or underlying configured fields, inspect raw ACP fields, or repair unsanitized 006 output; outer adapters may apply defense-in-depth only to data they independently know.
- Deriving a broader or different configured-value matcher than spec 005's normalized `redactionValues`, or detecting arbitrary unknown secrets that are absent from `redactionValues` and are not removed by structural projection or protocol-field classification.
- Adding vendor-specific behavior, remote transports, ACP v2, optional vendor extensions, permissions UI, or any other UI.

## Open questions

- **Approval blocker — event contract:** Should callers consume an `AsyncIterable` whose final item carries the terminal outcome, or a separate sanitized typed event stream plus outcome promise, and how is an indefinitely retained `cleanup_incomplete` run observed if an event consumer exits early? **Owner:** maintainer. **Resolution:** choose one public shape before approval and copy ordering, early-consumer-exit, cleanup-incomplete observation, and terminal-delivery rules into AC-5.
- **Approval blocker — cancelled-stop mapping:** How does `stopReason: cancelled` map when no caller cancellation or `runTimeoutMs` trigger occurred; how does a non-cancelled stop map after caller cancellation; and does an ACP cancellation acknowledgement after `runTimeoutMs` expiry preserve `timed_out`? **Owner:** maintainer. **Resolution:** approve a total local-trigger × ACP-stop mapping table before approval and use every row in AC-4, AC-6, AC-11, and AC-12.
- **Approval blocker — error precedence:** When a primary operation and completed cleanup both fail, the process exits while ACP rejects, or protocol failure races cancellation/`runTimeoutMs`, which condition supplies the eventual terminal tag/code and which become sanitized secondary diagnostics? A `cleanup_incomplete` result cannot itself terminalize or release ownership. **Owner:** maintainer. **Resolution:** approve a total error-precedence table before approval and use it in AC-8, AC-10, and AC-11.
- **Approval blocker — terminal-trigger precedence:** What linearization rule applies when normal completion, mapped ACP cancellation, caller cancellation, `runTimeoutMs` expiry, process exit, protocol failure, or a completed-cleanup failure become observable together? `cleanup_incomplete` delays emission but does not invent a second terminal trigger. **Owner:** maintainer. **Resolution:** approve a deterministic rule before approval and encode relevant pairwise races in AC-11.

# Configure named ACP agents

Status: draft
Approach: Define a source-independent version 1 agent map loaded through `ConfigurationSource` and a single `resolveAgent(name, requestedCwd, signal)` trust-boundary operation that returns a defensively immutable normalized profile with one readonly `redactionValues` classification or a typed, actionable, redacted error.
Source work item: none (trackerless project; user request dated 2026-07-24)

## Problem

pi-leash has only a generic configuration-source port and no user-facing contract for identifying or safely launching an ACP-compatible agent, so future delegation code cannot obtain a syntactically valid executable, fixed arguments, final policy-validated working directory, minimal environment, and bounded execution duration without inventing inconsistent defaults or passing untrusted values across the process-execution boundary. Configuration loading and resolution can also block before a profile's execution timeout is available, so that pre-execution phase needs its own host-level finite deadline. Specs 006 and 008 additionally need one policy-owned, size-bounded configured-value classification so exact cross-chunk redaction can remain finite without reconstructing sensitive-value policy from launch fields.

## User stories

- As a Pi user, I want to define multiple ACP agents by stable names so that I can select the intended local agent explicitly.
- As a security-conscious user, I want each agent to receive only a policy-approved working directory and explicitly defined environment so that caller context cannot silently broaden its host access.
- As a maintainer, I want one strict, versioned resolver contract with a pre-load cancellation and timeout boundary so that unsupported, malformed, or stalled configuration fails before any process starts.
- As a delegation implementer, I want one normalized profile containing the final working directory and execution-timeout budget so that one-shot orchestration does not reinterpret configuration policy.
- As a downstream sanitizer owner, I want one immutable, size-bounded `redactionValues` classification so that exact cross-chunk replacement has a finite pending-suffix bound and does not reinterpret the launch profile.
- As a user diagnosing configuration, I want errors to identify the affected agent and field with a recovery action while hiding sensitive values.

## Acceptance criteria

- AC-1: A valid logical version 1 configuration loaded through `ConfigurationSource` consists of `version` plus an `agents` mapping whose keys are the sole configured-agent identities. Each map value contains an executable, ordered fixed-argument list, working-directory policy, environment-forwarding list, environment-override map, and integer `runTimeoutMs`, and does not repeat a profile `name`. A successful resolution adds exactly one normalized configured-value classification field, `readonly redactionValues: readonly string[]`; no parallel configured-secret or prohibited-value collection is exposed. The exported normalized-profile types and every nested field are TypeScript `readonly`; the resolver defensively copies all source arrays and objects and recursively freezes the returned plain objects and arrays, including `redactionValues`, so mutation of source-owned references after loading or attempted mutation through runtime references cannot change a resolved profile.
- AC-2: Configuration access exposes the logical asynchronous boundary `resolveAgent(name, requestedCwd, signal)`. A finite host-level `configurationLoadTimeoutMs`, configured and available before the operation starts rather than read from an agent profile, anchors a configuration-resolution deadline at monotonic-clock entry to `resolveAgent`, before `ConfigurationSource.load` is invoked; that deadline covers loading, parsing, validation, agent selection, environment resolution, and working-directory policy resolution through successful return. The resolver passes `ConfigurationSource.load` an effective `AbortSignal` that aborts when either the caller's `signal` aborts or this deadline expires. Either event rejects without a partial profile or execution-boundary invocation; caller abort remains cancellation, while deadline expiry is a typed `configuration_timeout` error. OQ-7 resolves the exact finite value and host configuration surface before approval.
- AC-3: Configured-agent identity selection compares `name` exactly and case-sensitively against `agents` map keys; the returned profile has a readonly `name` copied from the matched key. Keys must satisfy the exact version 1 identifier grammar and length bound selected in OQ-5. Identity selection does not consult the filesystem, `PATH`, installed packages, vendor metadata, nested profile fields, normalized aliases, or fallback names; after identity selection, the distinct working-directory policy step in AC-5 may inspect filesystem existence, type, and symlinks.
- AC-4: Every configured executable is non-empty, NUL-free, and syntactically absolute under the supported-platform rules selected in OQ-6. A resolved profile preserves that executable as one direct-spawn value and preserves the fixed arguments as an ordered, frozen vector, including an empty vector; it performs no command-line parsing, shell interpolation, per-run argument injection, or executable discovery. Executable existence, file type, executability, supported-platform launch behavior, and launch-time TOCTOU revalidation belong to SPEC-004 and are not configuration-validity checks.
- AC-5: `resolveAgent(name, requestedCwd, signal)` treats `requestedCwd` as an untrusted caller candidate and applies the selected profile's working-directory policy exactly once within the configuration-resolution deadline. This policy step may inspect filesystem existence and type, resolve or reject symlinks, and compare the candidate or resolved path with permitted roots. Success returns one final, absolute, existing, policy-validated directory as `cwd`; failure returns a configuration-resolution error. Only this returned `cwd`, never the raw caller candidate or unresolved policy, is passed by SPEC-006 to SPEC-004. No current-process-directory fallback is permitted, and the policy vocabulary, permitted roots, relative-path behavior, missing-path behavior, directory-type checks, and symlink handling are resolved in OQ-2 before approval.
- AC-6: A resolved profile environment contains only host variables named by the profile's explicit forwarding list plus explicit profile overrides; it never inherits the complete ambient environment. Variable names and override values are validated and defensively copied before return. A resolved environment name or value may contribute to `redactionValues` only when it originates from an explicitly configured forwarding or override field and the OQ-8 security policy classifies it as sensitive; unselected ambient values never contribute, and downstream consumers do not infer a broader sensitive set from the environment object. Absent forwarded variables, forwarding/override collisions, unsetting, platform-specific name comparison, and prohibited sensitive variable names follow the semantics resolved in OQ-3 before approval.
- AC-7: Each configured profile has an integer `runTimeoutMs` within inclusive documented version 1 bounds. Configuration loading and resolution consume none of this budget. Immediately after `resolveAgent` returns successfully, and before SPEC-006 invokes SPEC-004 executable validation or acquires any process/ACP resource, SPEC-006 reads a monotonic clock once and anchors the execution deadline at `now + runTimeoutMs`; that deadline bounds launch and active delegation execution. Execution-deadline expiry is a terminal trigger rather than a promise that cleanup has already settled: SPEC-004's separately configured cleanup-stage bounds, such as graceful-close, terminate-wait, and forced-exit waits, govern bounded process cleanup and neither replace, reset, nor derive from `runTimeoutMs`. Tests accept both execution-timeout boundary values and reject a missing value, non-integer, non-finite value, zero or negative value, and values immediately outside either bound before execution; OQ-4 supplies the exact bounds before approval.
- AC-8: Validation or resolution fails closed before execution for a missing required field, wrong value type, null where a value is required, invalid agent-map key, empty, relative, platform-invalid, or NUL-containing executable, NUL-containing argument, invalid working-directory policy or requested-cwd resolution, invalid or NUL-containing environment name or override value, invalid execution timeout, any OQ-8-classified value whose normalized UTF-8 byte length exceeds the approved hard maximum or otherwise cannot satisfy the approved redaction-value rules, caller cancellation, or configuration-resolution timeout; a test execution boundary records zero invocations for every rejected case.
- AC-9: An absent or unsupported schema version, an unknown field at any version 1 object level, resolution of an undeclared agent-map key, and expiry of the configuration-resolution deadline each produce a typed error in the appropriate `unsupported_version`, `invalid_configuration`, `unknown_agent`, or `configuration_timeout` category rather than being ignored, coerced, defaulted, or reclassified as an execution timeout.
- AC-10: The source selected in OQ-1 uses a parser that reports duplicate keys/declarations before conversion to ordinary JavaScript objects and preserves a source location for every key and declaration. Validation rejects duplicate agent-map keys, duplicate fields, and duplicate entries in an environment-forwarding list before they can be overwritten or collapsed; diagnostics identify both preserved source locations without reproducing their values. A source path that first applies a parser equivalent to `JSON.parse` and therefore loses duplicate keys or locations does not satisfy this contract.
- AC-11: Every configuration or resolution error identifies its category, configuration source, agent when safely identifiable, safe field path or preserved declaration location, violated constraint, and a concrete recovery action. Error messages, causes, structured details, logs, and serialization never project structural executable, argument, working-directory-policy, requested-cwd, or resolved-cwd values; they may name the safe field path but must omit its value rather than relying on substring replacement. Those surfaces also expose neither the `redactionValues` collection nor any environment, authentication, credential-shaped, invalid raw-name, or other configured value classified sensitive by OQ-8. Automated tests use distinct synthetic sentinels and prove no prohibited value or collection appears in any diagnostic surface, including the error produced when a classified value exceeds its byte maximum.
- AC-12: The version 1 contract, `resolveAgent(name, requestedCwd, signal)` boundary, resolved location and format, agent-map identity and grammar, executable syntax and SPEC-004 validation handoff, working-directory behavior, environment behavior, host-level configuration-resolution timeout and anchor, profile execution-timeout bounds and anchor, distinct process-cleanup bounds, compatibility policy, immutability guarantees, `redactionValues` derivation and consumers, the hard UTF-8 byte maximum and fail-closed behavior, structural diagnostic non-projection, and the exact-match limit of the redaction guarantee are documented with synthetic non-secret examples; incompatible future contract changes require a new configuration version and the project's semantic-versioning treatment for public configuration contracts.
- AC-13: Focused automated tests use a controllable monotonic clock and cover successful loading and resolution, map-key identity, defensive-copy and frozen-runtime behavior including `redactionValues`, final-cwd filesystem resolution, caller abort, configuration-resolution timeout before/during each bounded resolution stage, the post-resolution execution-deadline anchor, proof that resolution time is not deducted from `runTimeoutMs`, and the boundary, invalid, unknown, duplicate, source-location, and sensitive cases above. Redaction-classification tests cover every approved source class, maximum-minus-one/maximum/maximum-plus-one UTF-8 byte boundaries with multibyte values, normalization and deduplication, empty values, platform cases, structural diagnostic omission, and proof that only the same readonly `redactionValues` classification is handed to SPEC-006 and SPEC-008; implementation evidence records the required red-green-refactor cycle, and `npm run check`, `npm run typecheck`, `npm run test:unit`, `npm run test:integration`, `npm test`, `npm run build`, and `npm pack --dry-run --json` all exit 0.
- AC-14: On successful resolution, `redactionValues` is derived only from resolved string values originating in configuration fields that the approved, version-pinned OQ-8 security policy classifies as sensitive; caller or agent text, unselected ambient values, and configured fields not so classified cannot be added heuristically. Each admitted member is validated using the policy's platform-independent UTF-8 measurement against one finite hard `maxRedactionValueUtf8Bytes`; if any value the classification requires would exceed that maximum or cannot be normalized or validated as specified, resolution fails with typed `invalid_configuration`, returns no profile, and invokes no execution boundary, without truncating, hashing, dropping, or partially returning the value. SPEC-006 and SPEC-008 consume only this readonly field as the configured-value input to their exact-match streaming redactors and derive a finite pending-suffix bound from the same hard maximum; they do not rebuild a broader matcher by walking executable, arguments, `cwd`, environment, or arbitrary profile fields. Across SPEC-005, SPEC-006, and SPEC-008 diagnostics, structural executable, argument, and raw or final working-directory values are non-projectable regardless of classification: a safe field label or path may be emitted, but never its value, and structural omission is not delegated to substring redaction. Exact replacement is guaranteed only for exact occurrences of members of `redactionValues`; no contract claims that arbitrary agent-authored text, unclassified configured strings, or transformed, encoded, or partial variants can always be discovered or scrubbed.

## Non-goals

- Implementing process spawning, executable existence/type/executability checks, launch-time TOCTOU checks, supervision, termination, cleanup timing, or output capture; these belong to SPEC-004.
- Implementing one-shot delegation orchestration or execution-deadline races; SPEC-006 consumes the normalized profile's final `cwd`, environment, and `runTimeoutMs` without redefining them.
- Deriving the host-level `configurationLoadTimeoutMs` from an agent profile or charging configuration loading/resolution against `runTimeoutMs`.
- Implementing ACP transport, protocol negotiation, sessions, prompts, capabilities, or lifecycle behavior.
- Registering or implementing Pi tools, commands, UI, mode-specific behavior, or agent-selection UX.
- Discovering executables, agents, manifests, installed packages, or configuration automatically.
- Storing, encrypting, prompting for, interpolating, or resolving secrets; environment overrides are plain values supplied by the chosen configuration source and remain subject to the approved sensitive-value classification.
- Detecting or guaranteeing removal of arbitrary secrets from agent-authored text when their exact values are absent from `redactionValues`; downstream content redaction is limited to the approved exact-value classification, while structural diagnostic fields remain non-projectable.
- Adding vendor-specific fields, aliases, defaults, protocol extensions, or harness branches.
- Supporting remote agents or non-local-stdio transports.
- Providing operating-system sandboxing or changing the permissions of a future child process.

## Open questions

Every unresolved question below blocks approval; its resolution must be copied into the affected acceptance criteria rather than left only in this section.

- OQ-1 — Configuration location, format, and preserving parser: Which file or Pi-provided source, precedence rule, serialization format, concrete version 1 document shape, and parser expose the logical agent map while preserving duplicate keys/declarations and source locations before ordinary-object conversion? Owner: maintainer. Resolution: choose and document one canonical source, format, and location-aware duplicate-preserving parser with malformed-input and duplicate examples before approval.
- OQ-2 — Working-directory policy: Which policies are available, how each uses or rejects `requestedCwd`, what roots they may resolve beneath, whether relative paths are allowed, and how non-existent paths, non-directory paths, and symlinks are handled? Owner: maintainer. Resolution: select a fail-closed policy vocabulary and add accepted/rejected candidate-to-final-cwd examples before approval.
- OQ-3 — Environment semantics: What happens when a forwarded variable is absent, when the same name is forwarded and overridden, whether explicit unsetting exists, how names compare across platforms, and whether any sensitive variable names are prohibited? Owner: maintainer. Resolution: define deterministic merge and validation rules that preserve the no-ambient-inheritance invariant before approval.
- OQ-4 — Execution-timeout bounds: What inclusive minimum and maximum values apply to profile `runTimeoutMs`, and is any per-agent default allowed? Owner: maintainer. Resolution: choose operationally bounded values; the recommended default is to require every profile to state an execution timeout explicitly, with no implicit or unlimited value, and keep configuration resolution and SPEC-004 cleanup-stage bounds separate.
- OQ-5 — Agent-name grammar: What exact ASCII or Unicode grammar, normalization policy, and minimum/maximum length apply to `agents` map keys? Owner: maintainer. Resolution: choose one finite grammar and length bound with accepted, rejected, case-distinct, and normalization-edge examples before approval.
- OQ-6 — Absolute executable syntax: Which operating systems are supported by version 1 configuration, and which POSIX-rooted, Windows drive-rooted, or UNC forms count as syntactically absolute when configuration may be authored on one platform and consumed on another? Owner: maintainer. Resolution: choose explicit platform/path parsing rules with accepted and rejected examples before approval; runtime existence, type, permission, and TOCTOU checks remain in SPEC-004.
- OQ-7 — Configuration-resolution timeout: What exact finite `configurationLoadTimeoutMs` value or allowed range applies, where is this host-level value configured before any agent configuration load, and may an embedding host override it within a hard maximum? Owner: maintainer. Resolution: select the configuration surface, default or required value, hard finite maximum, and synthetic-clock boundary examples before approval; it remains separate from every profile's `runTimeoutMs`.
- OQ-8 — Sensitive configured-value classification and redaction bound: Which version-pinned configured fields and values are sensitive and therefore contribute to `redactionValues`, what one finite positive `maxRedactionValueUtf8Bytes` applies, which UTF-8 encoder and invalid-scalar handling are used, whether normalization occurs before measurement, how ordering, equality, overlap, and deduplication work, whether classified empty values are rejected or omitted, and how supported-platform path, environment-name, case, and encoding semantics affect classification? Owner: maintainer. Resolution: approve one security-policy table and deterministic normalization algorithm, including its interaction with OQ-3; copy the exact rules into AC-1, AC-6, AC-8, and AC-11–AC-14 before approval; and add synthetic maximum, multibyte, empty, duplicate, and platform examples that let SPEC-006 and SPEC-008 derive their finite streaming pending-suffix bounds. Structural executable, argument, and working-directory diagnostic values remain non-projectable regardless of this classification.

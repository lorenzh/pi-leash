# Pi delegate tool adapter

Status: draft
Approach: Keep `src/pi/` as a synchronous, declarative adapter that registers one TypeBox-backed `delegate` tool, translates each invocation to the typed sanitized delegation contract exported by SPEC-006, and uses only Pi's standard tool update/result/error channels.
Source work item: none (trackerless project; user request dated 2026-07-24)

## Problem

pi-leash currently loads as a no-op Pi extension, so a Pi model has no typed, mode-independent way to select a configured ACP agent and submit a prompt through the delegation service. The missing adapter must expose that capability without moving configuration, ACP, process, lifecycle, secret-set sanitization, or presentation responsibilities into the Pi integration layer.

## User stories

- As a Pi model, I want one typed `delegate` tool so that I can send a prompt to a configured agent.
- As a Pi user, I want delegation cancellation and the active working directory to follow the invoking Pi tool call so that delegated work stops and runs in the expected project context.
- As a headless Pi integrator, I want standard tool progress, final results, and errors so that the same extension works in TUI, RPC, JSON, and print modes.
- As a maintainer, I want extension loading to remain side-effect-free apart from tool registration so that merely starting Pi cannot launch or retain delegated work.

## Acceptance criteria

- AC-1: Loading the source or compiled extension calls `pi.registerTool` exactly once with a tool named `delegate`, a human-readable label and description, and a strict TypeBox parameter schema; it registers no command, event handler, custom renderer, widget, message, or additional tool.
- AC-2: The registered schema and an explicit exported TypeScript input type agree on the exact input contract resolved in OQ-1. Validation computes `agent.trim()` and `prompt.trim()` only to require each result to be non-empty; unless OQ-1 explicitly selects normalization, validation does not replace either original value, and in particular the original prompt is passed unchanged to SPEC-006. Automated tests prove that missing required fields, additional fields, wrong types, empty strings, and whitespace-only agent identifiers or prompts are rejected before SPEC-006 is invoked, while accepted values containing surrounding whitespace retain their original code units at the service boundary under the recommended OQ-1 choice.
- AC-3: For a valid call, `delegate.execute` invokes the SPEC-006 delegation application service exactly once with the selected agent value and prompt determined by OQ-1, and supplies `ctx.cwd` only as the requested-working-directory candidate. SPEC-005 resolves that candidate against the selected agent's configured working-directory policy, and SPEC-006 passes only the resulting final validated working directory to lower layers. The adapter does not directly read configuration, resolve a final working directory, open ACP transport, or spawn or supervise a process; when SPEC-006 rejects an unknown or unavailable configured agent, no child process starts and no ACP turn begins.
- AC-4: A Pi-provided abort signal is forwarded to SPEC-006 without being replaced or detached. Focused tests cover a signal already aborted before invocation and a signal aborted while the service is running, but the terminal result follows SPEC-006's approved cancellation and terminal-trigger precedence. When cancellation is the provisional winner, any subsequent `cleanup_incomplete` state remains nonterminal under AC-5; only after SPEC-006 reaches true `terminal` with a sanitized cancelled outcome does the adapter report the call through Pi's failed-tool path, after which it emits no progress or success result. When completion or another failure wins first, the adapter preserves that eventual SPEC-006 terminal outcome and does not relabel it as cancelled.
- AC-5: SPEC-006 owns sanitizing every exported progress event through structural field exclusion, classified-sensitive-protocol-field removal, and exact replacement of spec 005 `redactionValues` and exposes those events only through a project-defined typed sanitized delegation contract. The adapter accepts that sanitized event type, translates each event into the exact partial-result contract resolved in OQ-2 and OQ-5, sends complete replacement snapshots only through the invocation's optional `onUpdate` callback, and keeps every snapshot within the limits resolved in OQ-4. When SPEC-006 exports `cleanup_incomplete`, `delegate.execute` remains pending, its event consumption remains attached to that same run, and lifecycle and highest-resource ownership remain exclusively with the SPEC-006 run owner. For each such event, when `onUpdate` exists the adapter emits a bounded sanitized replacement snapshot whose details contain the explicit discriminator `status: "cleanup_incomplete"`, distinct from ordinary running and terminal statuses; its text and details contain only the configured-agent identifier, bounded accumulated sanitized output or a stable adapter-authored cleanup-incomplete message, truncation state, and fields approved in OQ-2. The snapshot is progress only: the adapter returns no success result, throws no failed-tool result, invokes no cleanup operation, and releases no ownership or capacity until SPEC-006 reaches true `terminal`. As defense in depth, adapter-authored partial text and details use only allow-listed fields actually known to the adapter, omit the prompt, and sanitize or omit unsafe tool-input or tool-metadata values rather than echoing them. Tests prove that the adapter dependency receives no configuration object, configured environment values, raw secret set, raw protocol payload, raw lower-layer event, process handle, or cleanup capability.
- AC-6: SPEC-006 owns sanitizing every exported successful outcome through structural field exclusion, classified-sensitive-protocol-field removal, and exact replacement of spec 005 `redactionValues` and returns it through the typed sanitized delegation contract only after the run reaches true `terminal`. Only then does the adapter project that outcome into the exact final `AgentToolResult` contract resolved in OQ-2, with one standard text content block and explicitly typed, allow-listed details; empty output and truncated output are unambiguous, and both content and details stay within the limits resolved in OQ-4. Defense-in-depth tests use typed sanitized outcomes plus synthetic tool-input and metadata values to prove that bounding and projection do not add the prompt, raw invocation arguments, unapproved metadata, or an unsanitized duplicate; SPEC-007 does not receive or reconstruct the secret values used by SPEC-006.
- AC-7: Pi rejects schema failures before `execute`; SPEC-006 owns sanitizing every exported configured-agent, cancellation, and other delegation error through structural field exclusion, classified-sensitive-protocol-field removal, and exact replacement of spec 005 `redactionValues` and exposes only a typed sanitized error after true terminalization. Only then does the adapter throw that sanitized error, or an adapter-authored actionable wrapper containing only allow-listed sanitized fields, so Pi marks the tool result as an error rather than receiving success-shaped content. A `cleanup_incomplete` event is never thrown or returned as a terminal error, even when a cancellation, timeout, or failure trigger is already retained internally by SPEC-006. Adapter-authored validation/projection diagnostics identify the failed operation and recovery action without echoing the prompt, raw tool arguments, configuration, secret sets, or protocol payloads; tests cover sanitized terminal SPEC-006 errors and synthetic unsafe tool-input/metadata values without injecting raw configured secrets into the adapter.
- AC-8: Executing the factory performs no configuration load, secret-set or environment-value acquisition, filesystem access, process start, ACP connection, delegated run, timer, watcher, socket, or other background work. The first service call and any lower-layer work occur only after Pi invokes `delegate.execute`, and a terminally completed or failed invocation leaves no adapter-owned resource active. During orderly host or session shutdown, Pi is expected to abort the active invocation's existing signal and await `delegate.execute`; the adapter only forwards that signal and continues awaiting SPEC-006. If the run remains `cleanup_incomplete`, that invocation and the orderly shutdown wait may remain pending indefinitely while SPEC-006 retains its highest owner. The adapter registers no separate shutdown hook, calls no lower-layer close operation, and neither takes nor releases ownership. Forced runtime termination is host policy outside this result contract and does not authorize the adapter to synthesize a success or failed-tool result before termination.
- AC-9: Mode neutrality is verified by executing the same registered tool definition without reading `ctx.mode`, `ctx.hasUI`, or `ctx.ui`: a context test double fails on any access to those properties. With an `onUpdate` callback present, tests observe the expected standard partial `AgentToolResult` replacement snapshots, including the explicit `cleanup_incomplete` details status required by AC-5. With `onUpdate` absent, the same service input and eventual terminal result are observed without an update call or failure; a `cleanup_incomplete` run still remains pending rather than being converted into a terminal result. The adapter makes no UI call and adds no mode-specific branch, leaving TUI, RPC, JSON, and print presentation to Pi's standard handling of the same updates and final result.
- AC-10: Focused adapter tests record red-green-refactor evidence for registration, validation and value preservation, requested-cwd forwarding, cancellation precedence, typed sanitized progress/outcome/error projection, defense-in-depth handling of synthetic tool-input and metadata values, startup side effects, output bounds, and mode neutrality with `onUpdate` present and absent. Controllable SPEC-006 test doubles prove that `cleanup_incomplete` leaves `execute` unsettled, emits a bounded sanitized replacement snapshot with `details.status === "cleanup_incomplete"` only when `onUpdate` exists, invokes no adapter cleanup, and produces neither success nor failed-tool settlement until a later true terminal outcome; separate schedules cover later success, later failure or cancellation, no later cleanup proof, and host-shutdown abortion through the forwarded Pi signal. Contract tests prove that the SPEC-006 dependency exposes only sanitized event/outcome/error types and no raw configuration, secret-set parameter, process handle, descendant owner, or cleanup capability; synthetic configured-environment and classified-protocol-field sanitization tests belong to SPEC-006 rather than SPEC-007. The implementation change also updates README/status and architecture documentation as affected, and `npm run check`, `npm run typecheck`, `npm run test:unit`, `npm run test:integration`, `npm test`, and `npm run build` exit 0.

## Non-goals

- Implementing or changing SPEC-005, SPEC-006, or any configuration, ACP client/transport, owned-process, lifecycle, or harness-adapter layer.
- Applying structural field exclusion, removing classified sensitive protocol fields, or replacing spec 005 `redactionValues` in SPEC-006 events, outcomes, or errors; those responsibilities belong to SPEC-006 before values cross its exported typed contract.
- Reading or receiving normalized agent configuration, configured environment values, raw secret sets, raw sensitive protocol fields, raw protocol payloads, or a capability that reveals such values to the Pi adapter.
- Defining persistence, session restoration, durable tool details, output files, or run history.
- Adding run listing, run-status querying, resume, steering, replacement prompts, timeout policy, or run-management commands.
- Supporting parallel, chained, queued, or otherwise concurrent delegated calls as an adapter feature.
- Adding vendor-specific agents, protocol extensions, executable discovery, or harness installation.
- Adding TUI-only widgets, dialogs, notifications, custom components, or custom call/result renderers.
- Accepting arbitrary executables, working directories, environment variables, credentials, ACP payloads, or process options through the tool input.
- Detecting or claiming to redact arbitrary unknown secrets; adapter defense in depth is limited to tool input and metadata it actually knows, while SPEC-006 owns configured-environment and classified-protocol-field sanitization.
- Changing Pi's built-in tool execution or forced-termination policy, taking run or resource ownership during host shutdown, or implementing lower-layer cleanup and process supervision in `src/pi/`; the adapter only forwards Pi's invocation signal and awaits SPEC-006.

## Open questions

- OQ-1 — Exact input and normalization contract (owner: maintainer; resolve before approval): should the public schema be exactly `{ agent: string, prompt: string }` with `additionalProperties: false`, validate non-emptiness using `agent.trim().length > 0` and `prompt.trim().length > 0`, but pass both accepted original strings—including the original prompt's whitespace and code units—unchanged to SPEC-006? This is the recommended contract. If normalization is selected instead, approval must state separately whether the adapter trims the agent, the prompt, or both before invocation; an optional default agent, caller-supplied `cwd`, or run options remain not recommended because they expand configuration or run-management scope.
- OQ-2 — Remaining exact progress/final result shape (owner: maintainer; resolve before approval): the lifecycle invariant is fixed regardless of the selected shape: every cleanup-incomplete partial snapshot has a machine-readable details discriminator `status: "cleanup_incomplete"`, distinct from ordinary running and terminal statuses, while `delegate.execute` remains pending and no final result exists. Subject to that invariant, should every typed sanitized partial/final value contain one text block plus `DelegateToolDetails = { agent: string; status: "running" | "cleanup_incomplete" | "completed"; truncated: boolean }`, with ordinary progress text as the accumulated delegated output, cleanup-incomplete text as bounded accumulated sanitized output or a stable adapter-authored waiting-for-cleanup message, final text as the completed output, and `(no output)` for an empty completion? This remaining exact shape is recommended but unresolved; prompts, requested or final cwd, raw lower-layer errors, transcripts, protocol payloads, configuration, secret sets, process data, and cleanup handles would remain absent from details.
- OQ-3 — Requested working-directory source (owner: maintainer; resolve before approval): should the adapter expose no `cwd` input field and pass `ctx.cwd` only as the requested-cwd candidate to SPEC-006, with SPEC-005 selecting and validating the final cwd and SPEC-006 ensuring only that final value reaches process/ACP layers? This is recommended because it preserves Pi's active project context without allowing it to bypass configured cwd policy.
- OQ-4 — Output bounds and truncation (owner: maintainer; resolve before approval): should each typed sanitized accumulated progress snapshot and final text use Pi's head-truncation limits of 2,000 lines or 50 KB UTF-8, whichever occurs first, append an omission notice, set `truncated: true`, and discard rather than persist the omitted portion? This is recommended to match Pi's context limits while honoring this spec's persistence exclusion.
- OQ-5 — Cross-mode progress guarantee (owner: maintainer; resolve before approval): should the contract guarantee only standard `onUpdate` replacement snapshots when Pi supplies the callback, while an invocation without `onUpdate` returns the same final result and remains fully functional? This is recommended over UI calls or mode-specific output; Pi, rather than this adapter, determines whether TUI, RPC, JSON, or print presents intermediate updates.

# Retained in-memory ACP sessions

Status: draft
Approach: Add a Pi-independent application-core registry that acquires application-level reusable retained-session owners through an injected factory, linearizes `connect(transport, attemptSignal)` ownership, hands the create signal from startup into exactly the initial turn, consumes spec 005's bounded `redactionValues` contract for transient output sanitization, retains owners behind opaque IDs, and globally serializes all retained-session turns.
Source work item: none (trackerless project; user request dated 2026-07-24)

## Problem

pi-leash has boundaries for one-shot delegation and ACP communication but no application-core owner that can acquire and retain a reusable ACP session after a turn stops. Without that owner, callers cannot safely inspect retained work, send a later sequential follow-up, replace an active turn using portable cancellation, observe or retry eventual connection cleanup, or receive transient output without leaking normalized profile values, classified protocol fields, configuration, process, transport, or raw ACP behavior into registry or Pi integration code.

## Terminology

- An **ACP session** is the protocol session encapsulated and immediately owned by spec 003's reusable sequential ACP-session owner.
- A **retained-session owner** is the application-level typed owner returned by this spec's factory. It encloses the spec-003 connection/session owner, spec 005's finite bounded `redactionValues`, protocol-field classification, transient turn-output delivery, and process-independent close/eventual-closed behavior. It is not the raw spec-003 owner.
- A **retained session** is this spec's in-memory registry entry: an opaque registry ID, lifecycle state, and either one retained-session owner or one retryable partial-start cleanup owner. It is not durable across restart.
- A **retained turn event** is a project-owned sanitized value delivered transiently by a retained-session owner; it is never a raw or merely normalized ACP update.
- A **delegation run** is spec 006's independent one-shot operation. Creating or prompting a retained session does not create or schedule a delegation run.
- A **Pi/host session** is the outer host lifecycle. This spec has no Pi dependency; a future adapter must connect Pi/host-session shutdown and control surfaces to this registry.

## User stories

- As a caller, I want to create retained work using an agent name and requested working directory so that configuration resolution and startup remain behind an application-level factory boundary.
- As a caller, I want an opaque retained-session ID so that I can refer to a retained ACP session without learning its protocol or process identifiers.
- As a caller, I want to inspect a retained session so that I can decide whether a follow-up, cancellation, cleanup retry, or close operation is valid.
- As a caller, I want to send a follow-up only after the preceding turn stops so that prompts never overlap within an ACP session.
- As a caller, I want portable steering to abort the current turn before sending replacement work so that behavior conforms to ACP wire protocol v1.
- As a caller, I want cancellation and close operations to be safe to retry so that uncertain outcomes do not duplicate aborts or abandon owned resources.
- As a caller, I want my create cancellation signal to cover startup and the initial turn, then detach permanently, so that one create operation has continuous but bounded cancellation semantics.
- As a caller, I want transient typed turn output sanitized by the owner using spec 005's bounded redaction values and protocol classification so that neither registry nor outer adapters handle raw redaction values or ACP fields.
- As a host owner, I want shutdown to report incomplete cleanup without discarding ownership so that cleanup can be observed and retried until release is confirmed.
- As a maintainer, I want deterministic lifecycle, race, and synthetic-secret tests against application-level ports so that correctness does not depend on timing, credentials, or a vendor executable.

## Retained turn output and sanitization boundary

Each initial, follow-up, and replacement turn receives one turn-scoped `RetainedTurnOutputPort`. This project-owned typed push port accepts only a finite discriminated `SanitizedRetainedTurnEvent` union and has no operation for raw ACP updates, raw errors, `redactionValues`, matcher state, replay, or history. The factory-returned retained-session owner is the only component on this path permitted to consume spec 003's normalized updates. It sanitizes each value before invoking the output port; registry code may pass or route the port but cannot receive an unsanitized event or perform ACP-field interpretation.

The factory consumes exactly the finite readonly `redactionValues` returned by spec 005's normalized profile. It neither derives a broader matcher from executable, argument, cwd, environment, prompt, or other profile fields nor accepts caller- or adapter-supplied additions. Those non-exportable source fields remain excluded by the typed structural allowlist rather than being silently added to `redactionValues`; the canonical configured-agent designation remains the sole allowlisted profile identity. The raw `redactionValues`, matcher state, and source profile values never appear in a factory result, retained-session owner contract, registry state, event, error, diagnostic, or caller-provided output port. This contract claims exact replacement only for values supplied in `redactionValues` and makes no claim to detect arbitrary secrets or secret-shaped output outside those values and the classified protocol fields.

Spec 005 validates a finite hard maximum for every `redactionValues` entry and defines the shared streaming-sanitizer length unit and maximum. The retained-session owner consumes that contract unchanged: it rejects no valid profile by imposing a different maximum, accepts no value outside spec 005's bound, and retains at most the maximum-minus-one pending suffix in the same unit to prevent a cross-chunk partial match from being emitted early. It replaces every exact occurrence of a listed value with `[REDACTED]`, longest match first, including repeated, overlapping, and cross-chunk matches, and clears pending matcher content when the turn settles or delivery fails.

The retained-session owner also owns a total version-pinned classification for every field in spec 003's normalized update union. Protocol-sensitive fields are removed rather than copied; at minimum raw tool input/output, metadata, and location paths are not exportable. Every permitted string or nested structured value is sanitized against exactly `redactionValues` after classified-field removal and before delivery.

Only sanitized events are delivered, in turn order. Neither the retained-session owner nor registry retains delivered event content or full turn output for replay after delivery. Public terminal or control results may reference only a separately bounded summary derived from already-sanitized events; that optional summary is the sole permitted retained output, and its exact shape, bound, truncation, and delivery-failure behavior remain owned by the corresponding Open question.

## Acceptance criteria

- AC-1: The application core exports explicit typed contracts for creating, following up, steering, inspecting, cancelling, and closing retained sessions, transient sanitized turn output, and registry shutdown. The registry injects an application-level retained-session factory port and uses only the application-level retained-session owner or retryable partial-start cleanup owner returned by that factory. Registry production code imports neither configuration implementations nor spec 003 normalized-update types, the ACP SDK, ACP client/transport, raw process, or adapter contracts, and it does not encode, decode, classify, sanitize, name, or emit raw process or ACP methods. The factory implementation alone composes lower layers and wraps them behind the application owner. ID generation, turn-controller creation, clock, diagnostics, output routing, and registry policy are protocol-neutral injected dependencies.
- AC-2: The registry create input contains `agentName`, `requestedCwd`, `prompt`, caller `signal`, and one turn-scoped `RetainedTurnOutputPort`; that caller signal covers both factory startup and exactly the initial turn. Before invoking the retained-session factory, the registry validates the opaque-ID input policy, reserves live-session capacity, allocates a collision-checked retained-session ID, and records `starting`; capacity, ID-validation, or collision-exhaustion failure invokes no factory operation. The factory is invoked exactly once with `agentName`, `requestedCwd`, and `signal`; behind that application-level port it composes spec 005 agent/cwd resolution, spec 004 owned local-stdio startup, and spec 003 reusable sequential ACP-session creation, owns the startup deadline and cleanup of every partially acquired resource, and builds the retained-session owner's private sanitizer from exactly the normalized profile's finite bounded `redactionValues` plus the protocol classification. For spec 003 acquisition it derives one startup-attempt signal from caller cancellation and startup expiry and calls the exact `connect(ownedStdioProcess, attemptSignal)` contract. While connect is pending, the factory never races it by independently closing the transport: it aborts `attemptSignal` and awaits connect settlement. If cancellation wins spec 003's ownership linearization, connect rejects without transfer and the factory closes only the still-owned `OwnedStdioProcess`; if connect success linearizes first, that exact object transfers to the connection owner and every subsequent startup cancellation or failure before application-owner transfer closes only that highest owner. On successful application-level retained-session-owner transfer to the registry, one handoff linearization detaches every factory/startup listener from the create signal, permanently removes factory authority over later aborts, and installs a registry-owned one-shot bridge to the initial turn's registry-owned `AbortController`; an abort already observable at handoff or delivered afterward cannot be lost and calls that controller's abort path exactly once until the initial turn settles. The bridge is detached permanently when the initial turn reaches its validated terminal outcome or error, and any later abort of the create signal has no effect on the retained session or later turns. The bridge never closes a lower resource: cancellation, failure, close, and shutdown cleanup after transfer use only the retained-session owner. The factory returns exactly one of: a sanitized clean startup failure with no surviving owner, one retryable application-level partial-start cleanup owner, or one retained-session owner whose complete lower ownership chain and process-independent close/eventual-closed contract transfer to the registry. Only the successful retained-session owner starts the initial prompt with the registry-owned controller's signal and emits through the supplied output port. The retained-session ID is not derived from an ACP session ID, PID, executable, working directory, prompt, delegation-run ID, or Pi/host-session ID.
- AC-3: The observable retained-session states are exactly `starting`, `running`, `cancelling`, `steer_cancelling`, `steer_replacement_running`, `stopped`, `closing`, `cleanup_incomplete`, `closed`, and `failed`. Successful create follows `starting -> running -> stopped`; follow-up follows `stopped -> running -> stopped`; plain cancellation or a bridged create-signal abort during the initial turn follows `running -> cancelling -> stopped` when a validated stop permits it; steering follows `running -> steer_cancelling`, then only a validated `cancelled` stop permits `steer_replacement_running -> stopped`, while another validated stop returns directly to `stopped` without a replacement. A bridged abort that produces a turn error follows the existing failure/cleanup path rather than fabricating a stop. An explicit close follows any registered nonterminal state through `closing -> closed` only when release is confirmed. A startup, turn, cancellation, owner, or deadline failure first prevents further prompts and performs all required bounded cleanup attempts: confirmed cleanup permits terminal `failed`, while unconfirmed release enters nonterminal `cleanup_incomplete`, retains the relevant retained-session or partial-start cleanup owner, and permits only inspect, close retry, and registry shutdown. The registry continues observing only that application's process-independent eventual-closed signal; confirmed eventual closure linearizes a confirmation step through `closing` to `closed` or cleanup-confirmed `failed`, while a caller-triggered retry follows `cleanup_incomplete -> closing`, invokes only the highest owner's retryable close, and returns to `cleanup_incomplete` if release remains unconfirmed. Inspect is side-effect free and returns the opaque retained-session reference, exact state, a tagged sanitized last-stop value, cleanup-attempt/eventual-closed status, failure category, non-sensitive timing metadata, and at most the bounded sanitized summary allowed by this spec. A `closed` or cleanup-confirmed `failed` entry may be deregistered, after which inspect reports it as unknown.
- AC-4: A follow-up is accepted only while its retained session is `stopped` after a validated sanitized owner stop result. It atomically changes the entry to `running`, creates exactly one new turn `AbortController`, and invokes exactly one application-level prompt operation with that controller's signal and the follow-up's turn-scoped `RetainedTurnOutputPort`; any follow-up attempted in another state receives a typed state-conflict result without invoking the owner or output port. Raw spec-003 events and prompt results cannot cross that owner contract. The registry permits at most one prompt turn in flight globally across all retained sessions. Spec 009 schedules only independent spec 006 one-shot delegation runs; it neither wraps this registry nor removes this global retained-session gate, so retained-session concurrency remains excluded after spec 009.
- AC-5: Every initial, follow-up, and replacement turn has exactly one registry-owned `AbortController`, whose signal is the only turn-cancellation surface passed through the retained-session owner to spec 003's typed prompt operation. The create caller signal itself is never passed as the turn signal: after successful retained-owner transfer, its one-shot registry bridge shares the initial controller's exactly-once abort gate with plain cancel, steering, close, and shutdown, remains attached only until that initial turn's terminal outcome or error, and is never reused by a follow-up or replacement. Steering is accepted only in `running`, atomically enters `steer_cancelling`, and calls `abort()` on the active turn's controller exactly once; it does not call a `cancelCurrentTurn` owner API. It waits for that turn's validated sanitized stop result; only `stopReason: "cancelled"` permits creation of a new controller, transition to `steer_replacement_running`, and one replacement prompt invocation with the steering request's replacement `RetainedTurnOutputPort`. Every steering result exposes the required fields `state`, `replacementStarted`, `originalStop`, and `followUpAllowed` and may additionally expose only the optional bounded sanitized summary resolved under the Open questions; `originalStop` is the tagged union `{ status: "present", stopReason } | { status: "absent", cause }`. A non-`cancelled` validated stop returns `state: "stopped"`, `replacementStarted: false`, `originalStop: { status: "present", stopReason }`, and `followUpAllowed: true`; a deadline, close, shutdown, owner failure, or cleanup-incomplete outcome before a validated stop returns `replacementStarted: false`, `originalStop: { status: "absent", cause }`, and `followUpAllowed: false`. No registry code attempts a raw or vendor-specific steering method.
- AC-6: The first accepted plain cancel of a `running` retained session, or the one bridged create-signal abort while the initial turn is active, atomically enters `cancelling`, calls `abort()` on that turn's registry-owned controller exactly once, and waits for the actual validated owner stop result. A bridged abort racing a plain cancel, steering request, close, or shutdown shares the same abort gate and turn completion; duplicate cancel calls while `cancelling` cause no additional abort. Cancel of an already `stopped` retained session returns its existing stopped snapshot without an abort, abort of the detached create signal after initial-turn settlement is a no-op, and cancel in any other known state returns a typed state-conflict result. The active controller and create-signal bridge are discarded only after the initial turn settles and no replacement can use them. A stop that races cancellation determines the final state from the validated owner result rather than fabricating `cancelled`; every cleanup side effect uses only the retained-session owner.
- AC-7: Close is idempotent per cleanup attempt: the first close of a registered retained session prevents new prompts, suppresses a steering replacement not yet invoked, calls `abort()` at most once on any active turn controller, and invokes the highest acquired retained-session or partial-start cleanup owner's typed close operation once. It does not separately close configuration, raw ACP connection/session, transport, or process resources. Concurrent closes share that attempt. Confirmed release produces `closed`; a typed `cleanup_incomplete` result is nonterminal rather than permanently cached, retains the same highest owner and cleanup evidence, and keeps observing its process-independent eventual-closed contract. If eventual closure has not already confirmed release, a later close starts a new bounded owner-level cleanup attempt, allowing spec 003's connection close retry to reach its owned transport rather than returning a stale failure; confirmed eventual closure completes without any descendant call. Close of a cleanup-confirmed terminal or absent ID is a successful no-op. Neither `closed` nor `failed` is reported while lower ownership may remain live.
- AC-8: Registry shutdown has observable states `open`, `shutting_down`, `shutdown_incomplete`, and `shut_down`. The first shutdown atomically rejects new create, follow-up, steering, and plain-cancel operations, shares in-flight close attempts, and starts bounded close attempts for every other registered entry. It reports `shut_down` only when every owner confirms release through its close result or process-independent eventual-closed signal. If any entry remains `cleanup_incomplete`, shutdown returns a tagged incomplete report with the count, visibility-policy-compliant retained-session references, and at most permitted bounded sanitized summaries; it enters `shutdown_incomplete` and retains the registry entries and owners rather than claiming terminal shutdown or discarding them. Inspect, owner-level close retry, and another shutdown remain available, and a later shutdown retries only owners whose eventual closure is not already confirmed. Concurrent shutdown calls share one attempt. This operation does not observe Pi events itself and is not a substitute for the future Pi lifecycle/control adapter required below.
- AC-9: Inspect, follow-up, steer, and cancel of a well-formed but unissued or deregistered retained-session ID return the same typed `session_not_found` category without factory or owner effects. Oversized or structurally invalid references fail validation before lookup and are not echoed in errors or diagnostics. Opaque-ID collision retries are bounded, and exhausting them fails create before invoking the retained-session factory. A registered `cleanup_incomplete` ID remains known, consumes live-session capacity, and exposes retry status until cleanup is confirmed.
- AC-10: Overlapping retained-session operations have one deterministic atomic winner: application-owner transfer and create-signal abort cannot lose the abort or leave factory authority after transfer; a create-signal bridge, plain cancel, steer, close, and shutdown cannot duplicate the same controller abort; two follow-ups cannot both invoke prompt; close or registry shutdown prevents any prompt not already invoked and aborts an invoked turn at most once; and an initial-turn terminal result detaches the create bridge before any later create-signal abort can act. Losing operations receive a typed stopped, conflict, closing, cleanup-incomplete, or shutdown result rather than hanging, duplicating an abort/owner side effect, invoking lower cleanup, abandoning ownership, or producing an unhandled rejection.
- AC-11: The application-level factory owns the startup deadline and partial-start cleanup bounds; registry policy owns finite positive bounds for retained live sessions, active turns, cancellation wait, each close attempt, each shutdown attempt, ID-generation attempts, and any retained sanitized summary, with exact provenance and values resolved through the approval-blocking open questions. The sanitizer pending-suffix bound is not an independent registry setting: it is derived exactly from spec 005's validated hard maximum and length unit for finite `redactionValues`, and the factory/owner accepts no unbounded or alternate value source. Capacity rejection occurs before factory invocation. Expiry of any bound follows AC-3, AC-7, and AC-8 and cannot convert unconfirmed cleanup into a terminal result. Prompts, raw or normalized protocol content, delivered events, full streamed output, and transcript history are not retained after turn delivery/settlement; the only permitted output retention is the bounded sanitized summary. Sanitizer pending content is cleared on settlement or delivery failure. `cleanup_incomplete` entries continue consuming capacity, while cleanup-confirmed closed or failed entries do not.
- AC-12: The retained-session factory and owner sanitize before every registry or caller delivery. Transient events, public terminal/control results, inspect snapshots, factory/owner errors, shutdown reports, and diagnostics identify only the permitted operation, canonical sanitized agent designation, lifecycle state, cleanup completeness, failure category, recovery action, safe stop metadata, and optional bounded sanitized summary. They expose no prompt, undelivered or full streamed content, raw or normalized ACP update, classified protocol field, ACP session ID, delegation-run ID, Pi/host-session ID, command/argument, requested or resolved working directory, environment name/value, credential, authentication material, raw `redactionValues` or matcher state, unknown thrown value, or caller-supplied unknown ID. Structural exclusion protects prohibited source fields, and content replacement is claimed only for exact spec-005 `redactionValues`; diagnostic rendering of retained-session IDs remains redacted regardless of the open API-visibility decision.
- AC-13: Deterministic unit tests use injected IDs, fake clocks, controllable retained-session factory and owner fakes, observable `AbortController` test doubles, transient output-port captures, and explicit barriers rather than sleeps to cover every state and legal transition, `connect` cancellation-versus-transfer linearization, create-signal abort before application-owner transfer, at the handoff in both atomic orders, during the initial turn, racing plain cancel/steering/close/shutdown, and after initial-turn settlement, partial-start success/failure/cleanup-incomplete outcomes, connection eventual-closed observation and owner-level retry, validation and capacity before factory invocation, exactly-once turn aborts, permanent factory/bridge listener detachment, duplicate cancel/close/shutdown calls, shutdown-incomplete retention and retry, capacity and deadline bounds, unknown/malformed IDs, ID collisions, tagged present/absent steering stops, stop-versus-cancel, follow-up-versus-follow-up, cancel-versus-steer, close-versus-steer, and shutdown-versus-active-turn races. Parameterized synthetic-secret tests use exactly the finite `redactionValues` supplied by a normalized profile and classified protocol fields, including empty-list behavior, values at spec 005's maximum, nested values, repeated/overlapping strings, serialization, and maximum-length values split across two or more chunks; they prove only ordered sanitized events reach the port, `[REDACTED]` spans cross-chunk matches within the shared bound, no listed sentinel/classified field/raw `redactionValues` reaches any public or captured diagnostic surface, an unlisted permitted marker is not falsely claimed as detected, and no delivered content or sanitizer suffix remains after settlement. Architecture tests prove registry code has no configuration implementation, spec-003 normalized update, raw ACP, transport, process, Pi, or adapter dependency and emits no raw method.
- AC-14: Deterministic integration tests compose the registry with the production application-level retained-session factory, specs 005/004/003, and the compiled fake ACP agent to exercise agent/requested-cwd resolution, `connect(transport, attemptSignal)` cancellation on each side of ownership transfer, create-signal cancellation during startup, at application-owner handoff, during the initial turn, and after initial-turn settlement, a stopped retained-session follow-up on the same ACP session, `running -> steer_cancelling -> steer_replacement_running -> stopped`, non-`cancelled` and absent-stop steering suppression, partial-start cleanup, graceful close, cleanup-incomplete reporting, process-independent eventual-closed observation, and successful connection-owner cleanup retry. The fake normalized profile supplies finite bounded synthetic `redactionValues`, and the fake agent emits listed sentinels in one chunk, across chunks at the shared maximum, and inside classified tool fields; assertions prove transient output and any summary are sanitized, create abort reaches only the initial controller after handoff, all cleanup uses the retained owner, and the registry never receives raw updates or `redactionValues`. Tests run over local stdio without registry access to raw process or ACP methods, network access, real credentials, timing sleeps, installed vendor harnesses, abandoned ownership, retained full output, or leaked child processes.

## Non-goals

- Concurrent prompt turns within one ACP session or across retained sessions; spec 009 schedules only spec 006 one-shot delegation runs and does not change this exclusion.
- Persisting or restoring retained-session entries, ACP sessions, IDs, or lifecycle state across host or process restart.
- Implementing configuration parsing/resolution, deriving or extending spec 005's `redactionValues`, process launch, ACP encoding/decoding, raw methods, capability negotiation, transport, or child termination in registry code; the injected application factory composes specs 005/004/003 behind its port.
- Adding a separate `cancelCurrentTurn` method to spec 003's reusable ACP-session owner.
- Vendor-specific steering, non-cancelling mid-turn prompts, ACP v2, or remote transports.
- Creating, wrapping, or scheduling spec 006 delegation runs.
- Storing, replaying, or searching prompts, delivered events, full streamed output, transcripts, or conversation history; only transient sanitized event delivery and the explicitly bounded optional sanitized summary are in scope.
- Pi tools, commands, TUI, RPC/JSON/print presentation, notifications, or any other UI behavior.
- Implementing the future Pi lifecycle/control adapter, harness-specific user controls, or a user-facing configuration schema.
- Reattaching to an ACP process or ACP session after owner, transport, or child-process loss.
- Detecting arbitrary secrets or broadening content matching beyond exact spec-005 `redactionValues` and this spec's classified protocol fields.

## Future integration dependency

A future Pi lifecycle/control adapter, distinct from spec 007's one-shot delegate-tool adapter, must create or receive this registry, mediate retained-session control according to the approved ID-visibility and ownership rules, receive only `SanitizedRetainedTurnEvent` values and permitted bounded summaries, and call `shutdown()` when its Pi/host session shuts down. It must never receive raw `redactionValues`, matcher state, or normalized/classified ACP fields. It must treat `shutdown_incomplete` as nonterminal, retain access to the registry, expose or escalate the incomplete cleanup safely, and retry close/shutdown rather than discarding ownership. Implementing that adapter is outside this spec. Until it exists, retained sessions are an application-core capability only and are not usable or lifecycle-safe through Pi.

# Concurrent delegation scheduler

Status: draft
Approach: Place a Pi-independent, in-memory bounded scheduler around the SPEC-006 single-run delegation service, applying the admission policy and capacity scopes selected before approval while coordinating isolated requests, backpressure, cancellation forwarding, bounded observation, and non-abandoning shutdown.
Source work item: none (trackerless project; user request dated 2026-07-24)

## Problem

pi-leash has no application-level coordinator for multiple independent SPEC-006 single-run delegations, so concurrent submissions could oversubscribe local resources, corrupt scheduling state, starve queued work, leak sensitive run data through diagnostics, or be abandoned during cancellation and shutdown. Maintainers need a deterministic bounded scheduler that invokes SPEC-006 once per promoted request, retains responsibility while a promoted run has incomplete cleanup, remains independent of Pi and harness adapters, and never schedules SPEC-008 retained sessions or their turns.

## User stories

- As a Pi-independent application caller, I want independent single-run delegation requests admitted through hard capacity limits so that local execution remains bounded under load.
- As a caller with an accepted request, I want deterministic and fair queueing so that sustained later traffic cannot starve my run.
- As a caller, I want to cancel queued work or request cancellation of active work and receive one authoritative terminal outcome so that I can stop work without affecting unrelated runs.
- As a SPEC-006 service implementer, I want each scheduled request mapped to at most one isolated single-run owner so that failures, output, ACP sessions, cancellation, and incomplete cleanup cannot cross run boundaries.
- As a host lifecycle owner, I want shutdown to report incomplete cleanup while retaining the affected run owner and active slot so that a possibly live process is never hidden or abandoned.
- As an operator, I want bounded redacted current-state observations, ephemeral events, and separate diagnostics so that I can diagnose saturation and incomplete cleanup without exposing delegated content or changing run outcomes.
- As a maintainer, I want race-heavy behavior tested with controlled fakes rather than timing sleeps so that scheduler regressions reproduce deterministically.

## Approach options

All options schedule only independent SPEC-006 single-run delegations. They do not admit a SPEC-008 retained-session handle, retained-session turn, or follow-up prompt.

### Admission-order axis

1. **FIFO (recommended):** promote the earliest continuously eligible enqueue sequence. This has the simplest ordering and strongest starvation oracle.
2. **Priority with aging:** promote by explicit priority class, age bypassed requests deterministically, and use enqueue sequence for ties. This expands the public contract and remains out of scope unless selected before approval.

### Capacity-scope axis

1. **Global only:** enforce one active limit and one queue limit across all configured agents. This is simpler but permits one agent's requests to consume all capacity.
2. **Global plus per-agent (recommended):** enforce global limits and matching per-agent active and queue limits independently of the selected admission order. This adds configuration and eligibility rules while limiting noisy-neighbor effects.

## Acceptance criteria

- AC-1: The scheduler is usable in an automated test with only a typed SPEC-006 single-run delegation service test double and no Pi API, ACP transport, child process, or harness adapter. Its production contract accepts independent single-run requests only, exposes no operation for a SPEC-008 retained session or retained-session turn, and architecture checks reject imports into `src/pi/` or harness-specific adapters.
- AC-2: Scheduler configuration exposes documented finite defaults and finite absolute maximums. Concurrency values accept only integers greater than zero, queue values accept only integers greater than or equal to zero, omitted values resolve to the documented defaults, and invalid or above-maximum values fail validation before any request can be accepted.
- AC-3: The selected capacity model always enforces a finite global active-run limit and a finite global queued-request limit. If per-agent limits are selected, every admission simultaneously satisfies the global and matching per-agent limits. An active slot is acquired atomically when a request is promoted, immediately before its sole SPEC-006 invocation, and remains occupied while its run owner is `running`, `cleaning_up`, or `cleanup_incomplete`. The scheduler releases that slot exactly once only after the owner reaches a true terminal state with cleanup complete, records the owner's terminal outcome, and then promotes against updated capacity. A `cleanup_incomplete` observation is nonterminal and releases no slot. If invocation fails synchronously before a run owner is returned, the slot is released only after that scheduled request settles once as a typed start failure. Controlled concurrent submissions prove that no effective active or queue limit is exceeded at any transition.
- AC-4: Every accepted request receives a monotonic enqueue sequence, and the selected admission policy produces the same promotion order for the same ordered operation trace; enqueue sequence breaks all otherwise-equal choices. A request is continuously eligible across promotion opportunities when it remains queued and every selected per-agent capacity rule, if any, permits it immediately before each opportunity. At its first such opportunity, let `A` be the number of already queued requests ordered ahead of it and `Q` the effective global queue limit: FIFO must promote it by opportunity `A + 1`, and any selected priority-with-aging policy must promote it no later than opportunity `A + Q + 1`. Deterministic sustained-arrival tests run beyond the applicable bound and fail if the request has not started; an active slot held by `cleanup_incomplete` creates no promotion opportunity.
- AC-5: Each accepted scheduled request owns distinct mutable scheduler state, cancellation state, output routing, terminal delivery, and its sole SPEC-006 owner after promotion. Each SPEC-006 owner retains exclusive ownership of that independent run's ACP session and resources. Tests using distinguishable concurrent runs prove that output, completion, failure, cancellation, and incomplete cleanup affect only their owner; no ACP session or mutable state is shared between independent runs, and no SPEC-008 retained-session state is accepted or accessed. For a `cleanup_incomplete` run, the scheduler retains the owner reference and one current observation record until true terminal cleanup completes.
- AC-6: A submission is promoted exactly once when all selected active capacity is available, otherwise enters the queue exactly once when all selected queue capacity is available. A submission made when applicable capacity is full, including capacity held by `cleanup_incomplete` runs, receives the selected immediate typed overload outcome, distinguishable from a SPEC-006 run failure and safe to retry, without invoking SPEC-006, changing queue order, or exceeding a limit.
- AC-7: Cancellation that linearizes while a request is queued removes that request without invoking SPEC-006, preserves the relative order of remaining requests, frees its queue capacity, and settles the request exactly once as `cancelled`. Repeated queued cancellation is idempotent; queued cancellation is the only scheduler state guaranteed to select the `cancelled` terminal outcome.
- AC-8: A cancellation request that linearizes after promotion is forwarded at most once to that request's SPEC-006 run owner while it is nonterminal. The scheduler does not select, relabel, or replace the owner's outcome: it preserves `cleanup_incomplete` as a nonterminal state, keeps the request unsettled and active while that state persists, and publishes exactly the owner's approved `completed`, `cancelled`, `timed_out`, or `failed` terminal outcome only after cleanup completes. Repeated or post-terminal cancellation does not invoke the owner again or affect another request.
- AC-9: For cancel-versus-promotion races, cancellation before promotion produces the queued `cancelled` outcome, while promotion before cancellation forwards cancellation to SPEC-006 and preserves the state and outcome selected by SPEC-006's approved terminal-precedence and cleanup rules. Completion-versus-cancellation, timeout, process exit, cleanup confirmation, and failure races after promotion are parameterized by those SPEC-006 rules rather than re-decided by the scheduler. No trace invokes SPEC-006 twice, settles a request twice, or releases a slot twice; a request may remain intentionally unsettled only while its owner remains observably `cleanup_incomplete`.
- AC-10: A synchronous invocation failure before a SPEC-006 owner exists is contained to that scheduled request and produces one typed redacted scheduler start failure. After an owner exists, the scheduler preserves its exact state and eventual terminal outcome: `cleanup_incomplete` is never converted to `failed`, never treated as terminal, and never causes capacity release. Once true terminal cleanup completes, the scheduler releases capacity at AC-3's boundary, continues admitting eligible work, and remains usable until shutdown. A run-observation callback failure never changes any request state or outcome and instead emits a redacted `observer_failed` diagnostic on a separate ephemeral diagnostic channel; a failing diagnostic callback is contained without recursive reporting or scheduler failure.
- AC-11: The first shutdown request atomically stops new admission, gives every queued request one `cancelled` outcome without invoking SPEC-006, forwards one cancellation request to every nonterminal promoted SPEC-006 owner, and waits through each owner's bounded cleanup attempt. Owners that reach true terminal cleanup release their slots and deliver their authoritative outcomes. If any owner reports `cleanup_incomplete`, shutdown returns a typed `incomplete` report containing only its count, opaque scheduled-request IDs, and redacted reason codes; the scheduler remains in `shutdown_incomplete`, retains each affected owner, active slot, pending request completion, and current observation, and does not claim zero active work or completed shutdown. Later true terminal cleanup releases the retained slot and owner exactly once; repeated shutdown calls neither discard ownership nor duplicate cancellation, and report complete only after every promoted owner is truly terminal.
- AC-12: Deterministic submit-versus-shutdown, queued-cancel-versus-shutdown, active-cancel-versus-shutdown, cleanup-incomplete-versus-shutdown, cleanup-confirmation-versus-shutdown, owner-terminal-versus-shutdown, and simultaneous-owner-terminal traces prove that operations linearized before shutdown receive AC-11's queued or owner-controlled state/outcomes, operations linearized after shutdown receive the selected closed-scheduler outcome, and each capacity slot is released once at AC-3's boundary. All handles and promises settle after true terminal cleanup; while an owner is `cleanup_incomplete`, only its request completion remains pending and shutdown returns the explicit incomplete report rather than hanging or falsely settling it.
- AC-13: The scheduler exposes an immutable current snapshot plus ephemeral run-observation and diagnostic callbacks; it retains no transition, terminal-outcome, or diagnostic history after callback delivery. The snapshot contains scheduler phase, active and queued counts, and at most one current-state entry per active slot with opaque scheduled-request ID, lifecycle state, and machine-readable reason code; this retained current-state set is bounded by the configured active limit and keeps `cleanup_incomplete` owners observable until true terminal cleanup. Ephemeral run observations use the same allowlisted fields, and the separate diagnostic channel identifies scheduler or observer operation and a stable redacted code. All surfaces exclude prompts, delegated output, ACP payloads and session IDs, process IDs, command arguments, working directories, environment data, credentials, authentication material, raw cancellation reasons, and raw underlying errors.
- AC-14: Unit tests use a manually controlled fake SPEC-006 single-run service, explicit deferred owner states/outcomes, and deterministic sequence/clock inputs to exercise limit boundaries, selected queue order, AC-4's finite starvation oracle, queued and active cancellation, outcome preservation, failure isolation, bounded current-state observation and ephemeral diagnostic separation, all races named above, and shutdown. A controlled owner enters `cleanup_incomplete`; tests prove its slot, owner, pending completion, and current observation are retained, no queued request is promoted into that slot, shutdown reports incomplete, and a later true terminal-with-cleanup-complete transition releases and removes it exactly once. Tests use no wall-clock sleeps, random ordering, network access, real child processes, credentials, vendor harnesses, or retained sessions, and replaying the same trace produces the same invocations, transitions, diagnostics, and outcomes.
- AC-15: An integration test composes the scheduler with the deterministic SPEC-006 single-run delegation boundary and fake ACP agent, submits more independent requests than the selected active limit, and proves bounded promotion, per-run ACP-session isolation, authoritative outcome preservation, cancellation forwarding, and active-slot release only after true terminal cleanup without SPEC-008 retained sessions, external credentials, or installed vendor harnesses. A scripted unconfirmed-exit scenario proves the promoted run remains `cleanup_incomplete`, visible, owned, and capacity-consuming while shutdown reports incomplete; after deterministic exit confirmation, the owner reaches terminal, the scheduler releases the slot, and shutdown can report complete. Implementation evidence records focused red-green-refactor cycles, and `npm run check`, `npm run typecheck`, `npm run test:unit`, `npm run test:integration`, `npm test`, and `npm run build` all exit 0.
- AC-16: The implementation change documents the selected admission policy, capacity scopes, defaults and maximums, overload/closed outcomes, true-terminal active-slot boundary, cancellation and terminal authority, starvation oracle, bounded current-state observation and ephemeral event/diagnostic channels, `cleanup_incomplete` ownership, and complete-versus-incomplete shutdown reports. The documentation identifies a future Pi lifecycle adapter as a required downstream dependency that owns the scheduler in Pi, calls `shutdown()` when the Pi/host session ends, and continues observing any `shutdown_incomplete` scheduler until every retained SPEC-006 owner reaches true terminal cleanup; this spec neither implements that adapter nor claims Pi lifecycle integration.

## Non-goals

- Scheduling SPEC-008 retained sessions, retained-session turns, follow-up prompts, steering operations, or retained-session shutdown.
- Distributed, multi-host, or persistent queues; recovery of queued work after process restart.
- Priority classes, preemption, deadlines, or priority inversion handling unless OQ-1 explicitly selects priority-with-aging admission.
- Sharing an ACP session or other mutable run state between independent SPEC-006 delegations.
- Vendor-specific worker pools, harness pools, executable discovery, or vendor load balancing.
- Any configuration that permits unbounded concurrency, an unbounded queue, or unbounded observation/diagnostic history.
- Transferring a `cleanup_incomplete` run owner to an unspecified supervisor, discarding it, releasing its capacity, or representing it as terminal failure.
- Implementing or changing the SPEC-006 single-run service or its underlying ACP wire lifecycle, transport, or owned-process supervision.
- Implementing the future Pi lifecycle adapter, registering Pi tools or commands, rendering Pi UI, or defining Pi-mode behavior.
- Remote admission control, cross-process coordination, durable retries, automatic retries, or workload migration.
- Capturing prompts, delegated output, protocol payloads, environment data, or raw errors as scheduler telemetry.

## Open questions

- OQ-1 — **Admission order:** Choose FIFO (recommended) or priority classes with deterministic aging. This choice does not select capacity scopes. Owner: user. Resolution: select one before approval; if priority is selected, define its classes and aging calculation while preserving AC-4's `A + Q + 1` maximum promotion opportunity, and remove the corresponding non-goal.
- OQ-2 — **Capacity scopes:** Choose global limits only or global plus per-agent limits (recommended). This choice does not select FIFO or priority admission, and a finite global ceiling remains mandatory either way. Owner: user. Resolution: select the scopes and, if per-agent limits are selected, define the stable non-secret agent capacity key before approval.
- OQ-3 — **Defaults and maximums:** Confirm or replace the recommended defaults of 4 active and 32 queued globally, plus 2 active and 16 queued per agent if selected; confirm absolute maximums of 32 active and 1024 queued globally, plus 16 active and 256 queued per agent. Queue value zero remains valid. Owner: user. Resolution: record the selected values in AC-2/AC-3 and public configuration documentation before approval.
- OQ-4 — **Rejection API shape:** Choose a tagged admission result (recommended), a rejected promise, or a typed thrown error for overload and closed-scheduler outcomes. The immediate, typed, non-owning, redacted semantics in AC-6 and AC-12 are fixed. Owner: user. Resolution: select one shape and name its exported outcome/error codes before approval.

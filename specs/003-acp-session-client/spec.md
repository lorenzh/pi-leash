# Reusable ACP v1 session client

Status: draft
Approach: Wrap the official SDK's stable ACP v1 client in a project-owned reusable session port with attempt-scoped connect cancellation, one ACP session, at most one active turn, and finite retryable close attempts with eventual closure proof, so spec 006 can use one turn and close while spec 008 may retain the same port for sequential turns.
Source work item: none (trackerless project; user request dated 2026-07-24)

## Problem

pi-leash currently exposes only an ACP byte transport and an empty connection contract, so application code cannot initialize an ACP agent, create and retain one ACP session, run validated sequential prompt turns, consume trusted typed updates and outcomes, cancel an active turn, or release the protocol connection through one unambiguous resource owner without depending directly on SDK and wire details.

## User stories

- As an application-core implementer, I want a reusable typed ACP session port so that a one-shot run or retained-session service can use the same protocol boundary without importing SDK-specific types.
- As a run owner, I want to use one prompt turn and close the highest acquired owner so that one-shot delegation does not duplicate backing-resource cleanup.
- As a retained-session owner, I want to issue sequential prompt turns with at most one active turn and own each turn's cancellation controller so that later retention policy can reuse an ACP session without emitting protocol methods itself.
- As a maintainer, I want a finite version-pinned update mapping and fail-closed protocol errors so that untrusted agent output cannot enter the core unchecked or drift silently on SDK upgrades.
- As a connection owner, I want exact ownership transfer plus finite, observable, retryable hierarchical close attempts so that no cleanup caller hangs indefinitely and the highest owner remains retained until every descendant release is proven.

## Normalization oracle

For `schema-v1.20.0` as implemented by `@agentclientprotocol/sdk@1.3.0`, the public project-owned update union has exactly the following wire-to-core mapping. Nested values are represented by structurally equivalent project-owned types, not SDK aliases. Reserved `_meta` and unstable fields are deliberately not surfaced; their presence on an otherwise valid stable update does not alter the mapped value.

| Stable wire `sessionUpdate` | Project-owned discriminator | Preserved payload |
| --- | --- | --- |
| `user_message_chunk` | `message_chunk` with `role: "user"` | `content`, `messageId` |
| `agent_message_chunk` | `message_chunk` with `role: "agent"` | `content`, `messageId` |
| `agent_thought_chunk` | `thought_chunk` | `content`, `messageId` |
| `tool_call` | `tool_call` | `toolCallId`, `title`, `kind`, `status`, `content`, `locations`, `rawInput`, `rawOutput` |
| `tool_call_update` | `tool_call_update` | `toolCallId`, `title`, `kind`, `status`, `content`, `locations`, `rawInput`, `rawOutput` |
| `plan` | `plan` | `entries` |
| `available_commands_update` | `available_commands` | `availableCommands` |
| `current_mode_update` | `current_mode` | `currentModeId` |
| `config_option_update` | `config_options` | `configOptions` |
| `session_info_update` | `session_info` | `title`, `updatedAt` |

The schema-v1.20.0 experimental `plan_update`, `plan_removed`, and `usage_update` discriminators and unknown/vendor discriminators are not members of this port and produce a typed unsupported-update failure. Changing the pinned schema or SDK requires an explicit review of this table, its project-owned nested types, exhaustive compile-time matching, public-contract versioning impact, and one parameterized test case per accepted or rejected discriminator.

## Ownership and close contract

- The ACP boundary accepts exactly an `AcpTransport` with byte endpoints, idempotent `close(): Promise<void>`, and `readonly closed: Promise<void>`. That object is opaque to ACP code and may be a simple byte transport or a composite implementation that owns a child process or other backing resources. `closed` is the process-independent eventual-closure signal: it never rejects, resolves exactly once only when cleanup of the transport and all of its backing resources is proven, and remains pending while cleanup is incomplete. Concurrent transport `close()` calls share one active attempt; successful close resolves `closed` and is cached, while a typed failure with stable code `cleanup_incomplete` leaves `closed` pending and permits a later attempt after the active one settles. ACP code neither imports process types nor discovers, closes, or reports backing resources separately.
- `connect(transport, attemptSignal)` uses the caller-owned signal only for that acquisition attempt. Processing an abort and publishing successful connection resolution share one atomic linearization. Until successful resolution publishes, the caller remains the immediate owner of that exact transport. An already-aborted signal or an abort that linearizes first makes `connect` reject once with a typed connect-cancelled error after detaching and disposing only private partial SDK state; no late SDK success may resolve the promise, use the transport, or transfer ownership, and the caller closes the transport. If successful resolution linearizes first, ownership of that exact transport atomically transfers to the returned connection owner; the abort listener is detached, later aborts of `attemptSignal` have no effect, and later cancellation uses only a turn-specific signal or the connection's `close()` API.
- After transfer, the connection owner immediately owns the SDK connection and subsequently owns initialization, its single ACP session, and its active turn as descendants. It exposes `readonly closed: Promise<void>`, which never rejects and forwards eventual closure at the owner boundary: it remains pending across cleanup-incomplete attempts and resolves only when connection-local routing, SDK resources, the owned transport, and all transport backing resources have proven release. Callers never inspect or close the transport or its backing resources independently after transfer.
- Spec 006's run owner uses the reusable session for at most one turn: it closes the exact transport directly if `connect` never transfers ownership, or uses only the connection owner's `close()` and `closed` after transfer. Spec 008 may retain the connection owner across sequential turns and likewise uses only that owner's close/retry and eventual-closure surfaces.
- The first connection `close()` atomically marks the connection closing and rejects new initialization, session, or turn work. At that same linearization, every still-pending public operation settles according to the table below before any cleanup await. The one-time shutdown then: (1) initiates at most one best-effort `session/cancel` notification write when a turn is active, without waiting for a protocol response; (2) disposes active-turn and ACP-session update routing; (3) closes the SDK connection; and (4) invokes the owned exact transport object's `close()`. It does not send optional `session/close`. Every step is attempted even if an earlier step fails or remains pending.
- Each connection close attempt has one approved positive finite total bound, measured by the approved monotonic-clock policy from that attempt's linearization. Every connection-local or SDK cleanup await—including cancellation-write settlement, asynchronous routing disposal, SDK connection close/disposal, cleanup-error aggregation, and observation of their release proof—and transport `close()` plus transport-release proof share that one remaining budget; no step receives a fresh nested budget. Concurrent callers join the active attempt and do not reset its deadline. Pending cleanup work is safely observed after timeout so that a late settlement cannot create an unhandled rejection and may supply eventual release proof, but no active `close()` call waits beyond the attempt bound.
- Connection close is idempotent per active attempt. Concurrent calls share exactly one active attempt and its typed result; one-time protocol side effects never repeat, and each attempt invokes or joins each still-required idempotent cleanup operation at most once. The connection tracks separate process-independent release proof for connection-local routing, SDK resources, and the transport. If all release is proven within the attempt bound, a failure-free close succeeds and that success is cached; a non-`cleanup_incomplete` aggregate close failure may be cached only after all release is proven, with typed non-sensitive secondary diagnostics. If any local, SDK, transport, or backing-resource release remains unproven when the bound expires—or a cleanup operation earlier establishes that release is incomplete—the active attempt settles with the process-independent typed `cleanup_incomplete` close error, retains the connection owner, leaves `closed` pending, and does not cache that result as a terminal close failure.
- After a cleanup-incomplete attempt settles, a later `close()` starts a fresh bounded attempt that joins still-running cleanup and re-observes or retries only still-unproven idempotent local, SDK, and transport cleanup; it never repeats the one-time cancellation or routing side effects. Higher layers continue to call only the connection owner. Late proof from any prior attempt remains observable; once every local, SDK, transport, and backing-resource release is proven, connection `closed` resolves and successful closure is cached without descendant access. No initialize, session-new, prompt outcome, update iterator, or active close caller may hang indefinitely without its specified finite settlement.

| Pending operation when close linearizes first | Exact finite public settlement |
| --- | --- |
| `initialize` | Its promise rejects once at the close linearization with `{ kind: "closed", operation: "initialize" }`; any later initialize response is ignored. |
| `session/new` | Its promise rejects once at the close linearization with `{ kind: "closed", operation: "session/new" }`; no session handle is returned and any later session response is ignored. |
| `session/prompt` | Its outcome promise and update stream each settle once at the close linearization with `{ kind: "closed", operation: "session/prompt" }`; any later update or prompt response is ignored. |

A validated response that linearizes before closing begins retains its normal typed result: completed initialization remains completed, a completed `session/new` may return its session handle before that handle is immediately made closed by connection shutdown, and a completed prompt retains its normalized terminal outcome. The operation-versus-close winner is selected once; therefore these public races finish even when a close attempt or `closed` remains pending. Close-attempt results and eventual closure remain separate from those operation results.

## Acceptance criteria

- AC-1: `src/acp/` exports a strict-TypeScript, project-owned `AcpTransport` with `close()` and eventual `closed`, client factory, connection/session port with forwarded eventual closure and a finite close-attempt policy, turn request, finite normalized update union, terminal outcome, capability snapshot, and ACP client error types including typed connect cancellation and `cleanup_incomplete`; the port supports sequential turns on one ACP session with at most one active turn, while consumers import no `@agentclientprotocol/sdk` types, unchecked `any`, Pi APIs, process APIs, configuration types, or adapter/vendor branches, as verified by `npm run typecheck` and architecture unit tests.
- AC-2: Given an injected `AcpTransport` and caller-owned attempt signal, `connect(transport, attemptSignal)` establishes the SDK connection using the exact cancellation-versus-success linearization in the Ownership and close contract. If abort wins, connect rejects once with a typed connect-cancelled error, never later succeeds or transfers ownership, and leaves transport cleanup with the caller; if success wins, it returns one connection owner, transfers that exact transport, detaches the attempt signal, and ignores later attempt-signal aborts. The connection owner's required `initialize()` then sends `initialize` with ACP wire protocol v1 (`acp.PROTOCOL_VERSION`) and `clientCapabilities: {}` before any `session/new`; initialize failure occurs after transfer, becomes a typed initialize error, and initiates or joins the connection owner's active close attempt.
- AC-3: The client accepts an initialization response only when the SDK validates it and the negotiated protocol version equals the requested stable v1 version; omitted or empty agent capabilities become a project-owned snapshot with every optional feature unsupported, and advertised optional agent capabilities are recorded but do not add methods to this port. Because the client advertises no optional capabilities or request handlers, inbound `session/request_permission`, `fs/read_text_file`, `fs/write_text_file`, `terminal/create`, `terminal/output`, `terminal/release`, `terminal/wait_for_exit`, and `terminal/kill` requests receive JSON-RPC method-not-found (`-32601`) with no filesystem, terminal, permission, or other local side effect; the active turn may continue if the agent handles that response. Unit wire-trace tests cover omitted, empty, and advertised agent capabilities, every unsupported client-method family, and incompatible protocol version, and verify that no optional outgoing ACP method is sent.
- AC-4: After successful initialization, one call creates exactly one ACP session by sending `session/new` with a validated absolute working directory and no MCP servers; an empty/non-absolute path fails before the request, and `session/new` before initialization fails with a typed lifecycle error. That session accepts non-empty text prompts sequentially, sends one `session/prompt` per accepted call with the same session ID, and permits the next turn only after the prior turn reaches its terminal outcome or error. A prompt attempted while another turn is active, a second `session/new`, an empty prompt, or work after closing fails with a typed lifecycle/input/closed error and writes no corresponding protocol request; focused tests prove two successful sequential turns and rejection of overlapping turns.
- AC-5: For each turn, SDK-validated notifications for the active session are emitted in wire order and mapped exactly by the version-pinned Normalization oracle; updates from another session fail closed, each accepted discriminator has a parameterized exact-output test, each excluded experimental discriminator has an unsupported-update test, and an exhaustive compile-time guard prevents an SDK/schema discriminator change from compiling without an explicit mapping decision. The validated prompt response produces exactly one turn outcome: `cancelled` maps to the project-owned cancelled discriminator, and `end_turn`, `max_tokens`, `max_turn_requests`, and `refusal` map to the project-owned stopped discriminator while preserving the exact stop reason; no update is emitted for that turn after its outcome.
- AC-6: Protocol and transport failures become project-owned typed errors that identify the failed operation (`connect`, `initialize`, `session/new`, `session/prompt`, `session/update`, cancellation, or close), classify at least malformed input, incompatible version, unsupported capability/update, invalid lifecycle, closed connection, connect cancellation, transport failure, and `cleanup_incomplete`, omit sensitive protocol payloads, and provide a safe recovery indication. Abort or another failure before ownership transfer rejects `connect` after private SDK cleanup and leaves the exact transport cleanup to its caller; after transfer, malformed NDJSON and representative SDK-invalid initialize, session, update, and prompt responses poison the connection, settle affected work once, and initiate or join the active close attempt. Focused unit tests verify abort-before-success and success-before-abort ownership traces, prohibition of late transfer, and that higher-layer close/retry after transfer never bypasses the connection owner or duplicates effects within an attempt.
- AC-7: Each prompt accepts the only cancellation input exposed by this port: a turn-specific `AbortSignal` owned by the caller. If that signal aborts while its turn is active, the session sends exactly one `session/cancel`, continues accepting valid in-flight updates, and waits for the original prompt response without closing the reusable session; a `cancelled` response yields the normalized cancelled outcome, a different valid stop reason that wins the race is preserved, and the session may accept a later prompt with a newly owned signal. An already-aborted turn signal sends no prompt or cancel, repeated abort delivery sends no duplicate notification, and the port exposes no `cancelCurrentTurn` or equivalent cancellation method. Focused tests prove cancellation and cancel-then-next-turn behavior; spec 008 owns one `AbortController` per active turn and cancels by aborting it once.
- AC-8: `close()` and `closed` conform exactly to the Ownership and close contract during initialization, during `session/new`, during an active turn, between turns, after a terminal outcome, and after cleanup-incomplete. Focused race tests assert finite exact `{ kind: "closed", operation: ... }` settlement for initialize, session/new, prompt outcome, and update stream when close wins; the normal typed result when each response wins; settlement before the stated cancel/disposal/SDK/transport sequence; exact transport identity; no optional `session/close`; and all-step cleanup after injected failures. With the OQ-1 policy copied here before approval, deterministic fake-clock tests independently hold cancellation-write settlement, asynchronous local routing disposal, SDK close/disposal, aggregate cleanup handling, transport close, and each release-proof observer pending past the single total attempt bound; every case makes all concurrent active close callers receive typed `cleanup_incomplete` by that deadline, retains ownership, keeps `closed` pending, and produces no unhandled rejection. Further tests prove concurrent callers share one deadline and at most one invocation per required operation, one-time effects never repeat, a later call receives a fresh bounded attempt that can join eventual work or retry unresolved idempotent cleanup, late local/SDK/transport proof can resolve connection `closed`, higher layers use no descendant, proven success is cached, and no public iterator, request, or close call remains pending beyond its specified bound.
- AC-9: `npm run test:integration` exercises the production port against the deterministic fake ACP agent, verifies connect → initialize → one `session/new` → two sequential prompts on the same session, observes normalized text `fake-agent-ready` and terminal `end_turn` for each turn without cross-turn update leakage, calls only the connection owner's `close()`, observes its `closed`, and confirms the fake process exits with code 0 through the composite transport's close contract within the existing bound without forced cleanup, network access, credentials, or a vendor executable; capability, version, connect-cancellation, overlap, malformed-message, oracle, ownership-transfer, composite-transport, eventual-closure, retry, and close edge cases remain focused unit tests.
- AC-10: Implementation follows recorded red-green-refactor evidence; updates `README.md`, `docs/acp.md`, and `docs/architecture.md` for the reusable port, attempt-scoped connect cancellation, opaque/composite transport ownership, per-turn cancellation, the single total connection-close-attempt bound, eventual owner-level closure, retryable cleanup-incomplete attempts, normalization oracle, and finite operation-versus-close settlement; and leaves `npm run check`, `npm run typecheck`, `npm run test:unit`, `npm run test:integration`, `npm test`, `npm run build`, and `npm pack --dry-run --json` passing without changing the package file contract.

## Non-goals

- Spawning, supervising, timing out, terminating, configuring, or directly observing an ACP agent process; this feature accepts an opaque `AcpTransport`, and that transport's `close()` owns complete cleanup of any composite backing resources.
- Defining agent or harness configuration, executable discovery, environment construction, or working-directory existence/permission policy beyond requiring an absolute path at this port.
- Pi extension integration, tools, commands, TUI behavior, or other host-mode behavior.
- Deciding whether, when, or why to retain a session, issue a follow-up, replace a cancelled prompt, steer work, expire an idle session, or expose a session control API; those are multi-turn orchestration and retention policies outside this protocol port.
- Persistence across process or host restart, `session/load`, `session/resume`, or durable conversation storage.
- More than one ACP session per connection, concurrent prompt turns, connection pooling, or mutable-state isolation across separate connections.
- A connection-lifetime `AbortSignal` or a separate `cancelCurrentTurn` method. The factory signal is attempt-scoped only; after successful connect, cancellation uses the caller-owned signal supplied to an active prompt or the connection's `close()` API.
- Vendor-specific adapters or extensions, experimental ACP v2, remote transports, authentication, MCP servers, filesystem/terminal client capabilities, permission UI, or experimental schema-v1.20.0 session updates.
- Calling optional `session/close` in this version of the port.
- Choosing whole-run deadlines, process signals, process-kill policy, or lower transport-specific termination-stage bounds. This spec does own one process-independent finite connection-close-attempt bound covering every local, SDK, and transport cleanup await.

## Open questions

- **OQ-1 — approval blocker: finite connection-close-attempt policy.** What exact positive finite total bound governs one connection `close()` attempt, and what are its source, default, allowed minimum/maximum, monotonic clock, deadline anchor, boundary-tie rule, and test seam? The resolution must define one shared remaining budget for every cancellation-write, connection-local routing/disposal, SDK close/disposal, error-aggregation, transport-close, and local/SDK/transport release-proof await; concurrent callers must share the original deadline, while a later retry after `cleanup_incomplete` receives a fresh deadline without repeating one-time effects. It must also define how timed-out work is detached but safely observed, how late success/failure supplies eventual proof or diagnostics, which unresolved operations may be idempotently retried versus only rejoined, and how this owner-level bound composes with spec 004's lower transport termination-stage bounds and spec 006's separate whole-run deadline. The existing cooperative-turn question remains: spec 006 must define when its higher-level cancellation/deadline policy invokes explicit close if an agent never returns a terminal response after ordinary `session/cancel`; once explicit close begins, this finite attempt policy governs every cleanup await. Owners: spec 003 maintainer for the owner-level policy, with specs 004 and 006 maintainers for bound composition and higher-level escalation. Resolution: copy the exact policy and deterministic per-await timeout cases into AC-8 before approval. The invariant is not open: expiry with any release unproven settles every active close caller with typed `cleanup_incomplete`, retains the connection owner, keeps `closed` pending, and permits eventual proof or a later bounded owner-level retry; no active close call may hang indefinitely.
- OQ-2: Should a later application-facing delegation contract narrow this stable-field-preserving normalized ACP update union to a smaller presentation-oriented event set? Deferred to spec 006 and any later Pi adapter; owner: spec 006 maintainer. This protocol port preserves only the stable, version-pinned fields listed in its oracle and defines no UI projection.
- OQ-3: When spec 008 retains ACP sessions, should protocol cleanup evolve to invoke capability-gated `session/close`, or should retained-session shutdown continue to close only the connection owner; and should future schema updates amend this public mapping in place or add a versioned protocol adapter? Deferred to spec 008 before retained-session implementation and to the first ACP schema/SDK upgrade; owners: spec 008 maintainer and project maintainer. The current contract sends no `session/close` and remains pinned to schema-v1.20.0/SDK 1.3.0.
